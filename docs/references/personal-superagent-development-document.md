# 个人智能体终端引入 SuperAgent 开发文档

## 1. 文档说明

### 1.1 文档目的

本文档用于指导个人智能体终端的产品设计、架构设计、开发拆解、测试验收和分阶段交付。

文档重点描述：

- 系统的整体模块划分。
- 各模块需要实现的功能。
- 模块之间的职责边界和协作关系。
- 核心业务流程与状态变化。
- 安全、恢复、观测和评估要求。
- 分阶段建设范围与验收标准。

本文档不限定具体技术选型、产品名称、存储产品、代码结构或内部命名。

### 1.2 适用读者

- 产品经理与交互设计人员。
- 客户端、服务端和智能体运行时开发人员。
- 算法、模型与提示词工程人员。
- 安全、测试、运维和评估人员。

### 1.3 建设范围

建设一个支持桌面端、移动端、Web 和 IM 等入口的个人智能体系统。系统通过引入 SuperAgent 架构，使个人 Agent 能够：

- 跨渠道持续理解同一件工作。
- 同时推进多个互不干扰的任务。
- 在长任务执行期间接受新指令。
- 根据环境事件主动准备和处理事项。
- 在设备离线、进程异常或外部服务故障后恢复。
- 在人的授权、校准和验收下逐步扩大自主范围。

---

## 2. 产品定位与设计目标

### 2.1 产品定位

个人智能体终端是用户与持续在线 Agent 之间的统一交互入口。

SuperAgent 是终端背后的任务调度与执行体系，负责事件处理、任务管理、上下文组织、Worker 调度、工具执行、状态保存和异常恢复。

用户侧应始终感觉到自己在与同一个个人 Agent 协作，不需要理解底层的 Session、Worker 或任务进程。

### 2.2 核心设计目标

#### 连续

- 同一任务可以跨 IM、邮件、日程、文档和研发平台持续推进。
- 用户更换设备或入口后，不需要重复描述完整背景。
- 新事件能够关联到正确的已有任务。
- 系统能够区分历史资料、当前进展和已确认结论。

#### 高效

- 多个任务可以并行执行。
- 长任务执行期间，用户仍可发起新任务、补充要求或停止任务。
- 单个任务的执行细节不会污染其他任务的上下文。
- 用户能够集中处理需要决策和验收的事项。

#### 主动

- Agent 能持续接收已授权的环境事件。
- Agent 能判断何时行动、何时准备、何时等待、何时保持安静。
- Agent 能在没有正式指令时进行无副作用的准备。
- 主动行为必须符合用户角色、任务状态和已有负责人。

#### 持久

- Agent 的云端职责不依赖某台个人设备一直在线。
- 任务状态和交付物能够持久保存。
- 设备离线时，依赖该设备的步骤可以等待，其他工作继续推进。
- 系统异常后能够从明确的检查点恢复，并避免重复执行外部动作。

#### 可控

- 用户可以随时查看、暂停、接管和终止任务。
- 高风险动作必须经过明确授权。
- 记忆、偏好和长期规则可以查看、修改、作废和删除。
- 所有关键动作和异常恢复都应可审计。

### 2.3 非目标

第一阶段不以以下能力为建设目标：

- 无限制地自动操作所有外部系统。
- 完全无人监督的高风险决策。
- 复杂的多 Agent 自由通信网络。
- 将所有聊天内容自动转化为长期记忆。
- 通过扩大模型上下文替代任务状态和检索设计。
- 让终端用户直接管理底层会话和执行进程。

## 3. 核心概念与职责对象

| 概念 | 含义 | 主要职责 |
|---|---|---|
| 用户 | Agent 的所有者和授权者 | 提出目标、提供背景、授权、校准、验收 |
| Task | 用户需要推进的一件工作 | 管理目标、状态、优先级、等待条件和交付物 |
| Session | 模型运行时的上下文会话 | 承载 Router 或 Worker 的具体推理过程 |
| Router | 用户级全局协调入口 | 统一交互、任务关联、任务分派、跨任务协调 |
| Worker | 具体任务的执行者 | 规划、调用工具、推进任务、汇报状态 |
| Trigger | 外部环境或系统内部产生的事件 | 驱动任务创建、更新、等待或恢复 |
| Thread | 同一来源中的连续事件流 | 维护 IM 话题、邮件串、PR 等事件归属 |
| Artifact | 任务产生的交付物 | 保存文档、草稿、代码、分析结果和版本 |
| Live State | 任务近期运行状态 | 记录进展、下一步、等待条件和未结束事项 |
| Memory | 可跨任务复用的信息 | 保存背景、知识、决策、偏好和经验 |
| Personal Policy | 用户的个人化规则 | 管理当前重点、价值取舍、操作边界和 SOP |
| Device | 可被 Agent 使用的执行环境 | 提供文件、工具、网络或硬件能力 |
| Action Grant | 一次或一组动作的授权 | 限定动作、资源、范围和有效期 |
| Watchdog | 外部监控与恢复控制回路 | 发现异常、核对状态、恢复或升级人工处理 |

### 3.1 Task 与 Session 的关系

- Task 是面向用户的长期工作对象。
- Session 是面向模型运行的短期技术对象。
- 一个 Task 可以经历多个 Session。
- 一个 Task 默认由一个主 Worker 负责。
- 一个 Worker 可以在任务需要时创建内部 Subagent。
- 用户不需要通过 Session 管理工作。

## 5. 模块划分与功能需求

## 5.1 个人智能体终端模块

### 模块职责

为用户提供统一的对话、任务管理、授权、校准、验收和系统控制入口。

### 必须实现的功能

#### 统一对话

- 支持文字、语音、附件和链接输入。
- 支持用户只记录半个想法，不要求一次性形成完整需求。
- 支持在长任务执行期间插入新指令。
- 支持将当前输入指定为新任务或已有任务的补充。
- 支持用户纠正 Agent 对目标的理解。
- 支持查看 Agent 当前需要用户回答的问题。
- 支持跨终端继续对话和任务。

#### 任务中心

- 展示任务的当前状态、目标、负责人和下一步。
- 展示任务正在等待用户、他人、设备还是外部服务。
- 展示任务最新交付物和关键状态变化。
- 支持暂停、恢复、取消、接管和重新分派任务。
- 支持按活跃、等待、待验收、已完成和异常分类查看。
- 支持查看任务关联的消息、邮件、文档和其他来源。
- 支持用户调整任务优先级和完成标准。

#### 审批中心

- 集中展示需要用户授权的动作。
- 说明动作目的、影响对象、执行范围和潜在风险。
- 对文件修改、内容发布等动作提供差异预览。
- 支持批准、拒绝、修改后批准和转为仅生成草稿。
- 支持一次性授权、任务范围授权和限时授权。
- 支持撤销尚未执行的授权。
- 保留审批结果和实际执行结果。

#### 记忆与个人化中心

- 查看 Agent 使用的用户背景和当前重点。
- 查看记忆的来源、生成时间、确认状态和适用范围。
- 支持确认、修改、作废和删除记忆。
- 支持区分稳定偏好与特定条件下的临时决策。
- 支持管理价值取舍、通知习惯和操作边界。
- 支持管理按任务类型生效的 SOP。
- 支持查看哪些长期规则正在影响当前任务。

#### 设备与环境中心

- 展示设备在线状态。
- 展示设备可提供的文件、工具、网络和硬件能力。
- 展示哪些任务正在等待某台设备。
- 支持启用、停用和撤销设备接入。
- 支持限制设备可被哪些任务使用。

#### 交付物中心

- 集中展示文档、邮件草稿、代码、实验结果等产物。
- 支持版本对比和来源追踪。
- 支持下载、复制、继续修改和提交验收。
- 支持区分草稿、待验收和已正式交付的版本。

### 模块边界

- 终端不直接执行任务调度。
- 终端不直接保存唯一的任务状态。
- 终端不暴露 Worker 的内部推理过程。
- 终端只展示对用户决策有帮助的运行信息。

---

## 5.2 渠道接入模块

### 模块职责

将不同消息和工作平台转化为统一的事件输入与交付输出。

### 必须实现的功能

- 建立统一的渠道接入和断开机制。
- 维护用户在不同渠道中的身份映射。
- 将不同来源的消息转换为标准 Trigger。
- 保留原始来源、发生时间、权限范围和可信等级。
- 支持事件去重和重复推送处理。
- 支持断连后的增量同步。
- 支持来源内容的摘要和完整内容分离。
- 支持按渠道特点格式化输出。
- 支持输出失败后的重试和状态回报。
- 支持权限变化后停止读取或交付。

### 渠道输出要求

- IM：短结论、直接问题、低打扰。
- 邮件：完整背景、明确行动项和结构化正文。
- 文档：保留标题、段落、引用和版本信息。
- 研发平台：包含问题背景、修改说明和验证结果。
- 终端：提供可交互的任务、审批和交付物视图。

### 模块边界

- 渠道模块不负责判断任务归属。
- 渠道模块不直接调用 Worker。
- 渠道模块不自行扩大用户在原平台中的权限。

---

## 5.3 事件处理中心

### 模块职责

对持续进入的事件进行去重、过滤、分类、关联和分发。

### 必须实现的功能

#### 事件准入

- 根据来源、用户、群组、权限和订阅范围进行准入。
- 过滤重复事件和无处理价值的系统通知。
- 对事件设置可信等级。
- 对频率过高的事件进行合并或限流。

#### 语义分类

- 判断事件是否与用户有关。
- 判断是否需要用户关注。
- 判断是否与现有任务有关。
- 判断是否已有其他负责人。
- 判断应该行动、准备、等待、记录还是忽略。
- 输出分类依据和必要的置信信息。

#### Thread 管理

- 将同一话题、邮件串或研发对象下的连续事件组织为 Thread。
- 支持一个 Task 关联多个 Thread。
- 支持 Thread 的合并、拆分和重新归属。
- 支持 Thread 与 Worker 之间建立订阅。
- 支持事件超出任务范围时取消订阅或交回 Router。

#### 事件分发

- 已有明确归属的事件直接发送给对应 Worker。
- 新事件和跨任务事件发送给 Router。
- 保留 Router 所需的全局事件视图。
- 支持高优先级事件优先处理。
- 支持 Router 对积压事件进行批量判断。
- 支持事件重放和处理历史追踪。

### 模块边界

- 事件中心不负责具体执行任务。
- 语义分类不应直接产生高风险外部动作。
- 直通机制用于降低协调成本，不应绕过权限检查。

---

## 5.4 Router 模块

### 模块职责

作为用户级统一交互和全局协调入口，维护跨任务连续性。

### 必须实现的功能

- 统一承接来自各入口的人类交互。
- 判断输入属于新任务、已有任务还是跨任务事项。
- 创建、暂停、恢复和回收 Worker。
- 管理任务之间的依赖和优先级。
- 汇总 Worker 的状态和关键结论。
- 统一向用户输出，不暴露多个 Worker 的混乱过程。
- 维护用户级任务索引和近期全局状态。
- 对批量事件进行统一分派。
- 在无法确定任务归属时请求用户澄清。
- 在任务异常或目标冲突时升级人工处理。
- 控制单个用户的事件、任务和模型成本预算。

### Router 决策类型

- 忽略事件。
- 仅记录事件。
- 更新已有任务。
- 创建新任务。
- 进行后台准备。
- 请求用户补充信息。
- 请求动作授权。
- 暂停或终止任务。
- 将异常交给 Watchdog 或人工处理。

### 模块边界

- Router 不直接执行具体业务任务。
- Router 不直接操作高风险工具。
- Router 不替代完整的长期记忆系统。
- Router 不负责 Worker 内部的步骤拆解。

---

## 5.5 Task 管理模块

### 模块职责

将用户的工作转化为可持久化、可恢复、可验收的任务对象。

### 必须实现的功能

- 创建任务并记录目标、来源和完成标准。
- 管理任务负责人和当前执行者。
- 管理任务优先级、期限和资源预算。
- 管理任务之间的依赖关系。
- 保存任务当前阶段和下一步动作。
- 保存任务等待条件。
- 保存任务检查点和恢复信息。
- 管理任务暂停、恢复、取消和接管。
- 管理任务验收和完成状态。
- 管理任务关联的 Thread、Artifact 和 Memory。
- 对任务状态变化保留完整历史。
- 防止重复事件创建重复任务。

### 任务状态要求

系统至少应区分：

- 已接收。
- 已完成路由。
- 执行中。
- 等待用户输入。
- 等待动作审批。
- 等待他人处理。
- 等待设备上线。
- 等待外部服务。
- 待用户验收。
- 已完成。
- 恢复中。
- 已失败。
- 已取消。

### 模块边界

- Task 管理模块不执行模型推理。
- Task 管理模块不决定具体工具参数。
- 任务状态不能仅存在于模型聊天上下文中。

---

## 5.6 Worker 运行时模块

### 模块职责

在隔离上下文中推进具体任务，并向 Router 汇报可理解的状态。

### 必须实现的功能

- 为每个 Worker 加载明确的任务目标和完成标准。
- 建立任务独立的上下文空间。
- 按任务范围加载所需工具和资料。
- 支持任务规划、执行、观察和修正。
- 支持异步启动和停止耗时工具。
- 支持工具结果以事件形式返回。
- 支持执行期间接收新要求。
- 支持保存任务检查点。
- 支持按任务预算限制执行时间和调用次数。
- 支持重复动作检测和无效循环退出。
- 支持必要时创建内部 Subagent。
- 支持向 Router 汇报进展、异常和交付物。
- 支持用户暂停、接管和终止。
- 支持任务结束后释放不再需要的资源。

### Worker 汇报内容

- 当前任务阶段。
- 已完成事项。
- 下一步动作。
- 当前等待条件。
- 已产生的交付物。
- 需要用户决策的问题。
- 已发生或即将发生的外部副作用。
- 当前风险和异常。

### 模块边界

- Worker 默认不直接对用户输出。
- Worker 之间默认不自由通信。
- Worker 不应绕过 Task 和权限模块直接写入共享状态。
- Worker 内部 Subagent 对 Router 保持透明。

---

## 5.7 上下文组织模块

### 模块职责

在有限模型窗口和持续增长的任务信息之间进行取舍。

### 必须实现的功能

- 根据当前任务和步骤选择需要注入的信息。
- 将近期高相关信息直接放入当前上下文。
- 将长内容和低频内容保留为摘要与引用。
- 为 Trigger、Thread、Task、Worker 和 Artifact 建立关联。
- 支持从当前对象逐跳找回相关背景。
- 支持在需要核对时回到原始材料。
- 控制默认注入的信息量。
- 防止旧重点和不相关任务干扰当前任务。
- 支持上下文预算和截断策略。
- 支持记录模型实际使用了哪些关键资料。

### 模块边界

- 上下文组织不等于长期记忆。
- 摘要不能替代需要精确核对的原文。
- 检索结果必须保留来源与权限信息。

---

## 5.8 Live State 与长期记忆模块

### 模块职责

支持任务接续、个人化和跨任务经验复用。

### 必须实现的功能

#### Live State

- 记录刚完成的工作。
- 记录发生的重要变化。
- 记录尚未结束的事项。
- 记录当前下一步和等待条件。
- 记录已确认判断与仍待讨论的问题。
- 支持其他设备或新的 Worker 接手。
- 支持定向交接和补充说明。

#### 长期记忆

- 区分用户背景、当前重点、历史事件、稳定知识和经验规则。
- 保存记忆来源和适用范围。
- 保存结论成立的条件和必要背景。
- 支持记忆确认、修改、合并、作废和删除。
- 支持记忆有效期和重新确认。
- 支持区分草稿、已确认和已失效状态。
- 防止未确认推断自动成为长期事实。
- 防止多个 Agent 同时写入造成相互覆盖。
- 支持用户查看记忆对当前任务的影响。

#### 个人化规则

- 管理用户稳定背景。
- 管理当前关注重点。
- 管理冲突情况下的价值取舍。
- 管理工具操作边界和需要确认的动作。
- 管理按任务类型加载的 SOP。
- 支持规则修改后在后续任务中验证效果。

### 模块边界

- 不应将所有对话自动写入长期记忆。
- 不应只保存最终结论而丢失关键决策条件。
- 记忆系统不能成为绕过权限访问原始资料的入口。

---

## 5.9 主动策略与投机准备模块

### 模块职责

根据环境信号提前准备有价值的工作，同时控制打扰和副作用。

### 必须实现的功能

- 配置不同来源和场景的主动策略。
- 评估事件与用户当前关注的相关性。
- 判断用户、Agent 和其他负责人的角色。
- 判断任务当前是否允许进一步推进。
- 评估准备工作的预期价值和成本。
- 在无副作用模式下检索资料、生成草稿或运行实验。
- 在交付前再次检查准备结果是否有价值。
- 对低价值结果保持安静或丢弃。
- 对准备工作设置预算、期限和停止条件。
- 支持用户反馈“过早”“过晚”“不应介入”或“应该继续”。
- 根据反馈调整主动策略。

### 投机准备允许的动作

- 阅读已授权资料。
- 汇总内部信息。
- 生成邮件或文档草稿。
- 生成修改建议。
- 在隔离环境中运行可重复的实验。
- 准备正式动作所需的差异和影响说明。

### 投机准备禁止的动作

- 未经批准发送或发布内容。
- 未经批准修改共享资源。
- 将推测当成用户正式要求。
- 使用未授权凭据或设备。
- 因准备动作而干扰已有负责人。

---

## 5.10 工具与动作执行模块

### 模块职责

统一管理 Agent 可使用的工具、动作授权、执行结果和副作用核对。

### 必须实现的功能

- 注册工具能力、参数要求、风险等级和适用环境。
- 按任务和用户权限提供最小工具集合。
- 将准备动作与正式执行动作分离。
- 在执行前说明动作对象、范围和副作用。
- 对需要审批的动作验证有效授权。
- 支持查询工具执行状态。
- 支持外部服务超时和结果不确定状态。
- 支持故障后核对动作是否已经生效。
- 对重复请求进行幂等控制。
- 对工具返回内容进行安全过滤。
- 保存工具调用、审批和执行结果之间的关联。
- 支持紧急停用某个工具或某类动作。

### 模块边界

- 模型不能直接绕过工具权限层访问资源。
- 工具调用成功返回不应成为唯一的结果核对手段。
- 准备阶段生成的草稿不代表已获得执行授权。

---

## 5.11 执行环境与设备接入模块

### 模块职责

让云端 Agent 按需使用真实工作环境，并处理设备间歇在线。

### 必须实现的功能

- 管理云端和端侧执行环境的注册与状态。
- 描述各环境可用的文件、工具、网络和硬件能力。
- 根据任务需求选择合适环境。
- 支持端侧 daemon 主动建立安全连接。
- 支持端侧只执行被授权的命令。
- 支持设备离线时将相关步骤置为等待。
- 支持设备重新上线后的能力上报和任务恢复。
- 支持切换环境前检查任务依赖是否满足。
- 支持执行结果和交付物回传。
- 支持撤销设备接入和使未执行命令失效。
- 支持端侧资源使用和执行时间限制。

### 模块边界

- 端侧 daemon 不应成为唯一的任务状态来源。
- 不应默认所有设备可以互相替代。
- 不应为了云端执行而复制不必要的完整本地环境。

---

## 5.12 身份、权限与安全模块

### 模块职责

保护用户数据、设备、凭据和外部动作，建立明确的信任边界。

### 必须实现的功能

- 对用户、设备、渠道和任务进行身份识别。
- 将权限限制到具体用户、任务、资源和动作。
- 支持一次性、限时和任务范围授权。
- 支持授权撤销和权限到期。
- 对外部内容标记可信等级。
- 防止外部文本中的指令直接改变系统规则或触发高风险工具。
- 对敏感信息进行最小化读取和按需使用。
- 通过受控方式使用凭据，避免凭据进入模型上下文。
- 对输出进行敏感信息检查。
- 对共享资源的并发修改进行协调。
- 对关键操作保留审计记录。
- 支持全局停止和按任务停止。
- 支持安全事件下快速隔离设备、渠道或工具。

### 动作分级要求

| 动作等级 | 示例 | 默认处理 |
|---|---|---|
| 低风险读取 | 搜索、读取已授权资料 | 自动执行并记录 |
| 可逆准备 | 分析、草稿、隔离实验、可逆修改 | 自动执行，支持撤销 |
| 外部写入 | 发送、发布、共享修改、删除 | 明确审批 |
| 高敏感操作 | 支付、凭据、权限和批量操作 | 强确认或禁止 |

---

## 5.13 Watchdog 与异常恢复模块

### 模块职责

在主系统之外持续检查基础设施和任务进展，并执行受控恢复。

### 必须实现的功能

#### 基础设施监控

- 检查服务、接口和队列状态。
- 检查任务状态保存是否异常。
- 检查渠道和设备连接状态。
- 检查外部依赖是否持续失败。
- 检查任务是否超过时间或资源预算。

#### 任务进展监控

- 检查任务是否长时间没有新检查点。
- 检查是否反复执行相同动作。
- 检查是否反复修改但没有接近完成标准。
- 检查执行方向是否偏离任务目标。
- 检查是否应升级给用户处理。

#### 异常恢复

- 暂停可能继续产生副作用的动作。
- 读取最近的任务检查点。
- 核对上一条工具调用是否已经生效。
- 选择继续、重试、重新分派或人工接管。
- 防止恢复过程中重复发送、重复提交或重复修改。
- 记录异常原因、恢复动作和最终结果。
- 对无法恢复的任务保持明确失败状态。

### 模块边界

- Watchdog 不应无限制修改生产系统规则。
- 模型判断不能替代确定性的健康检查。
- 恢复不能以牺牲审计和权限要求为代价。

---

## 5.14 通知与交付模块

### 模块职责

将任务状态、待办决策和交付物以适合渠道的方式提供给用户。

### 必须实现的功能

- 区分需要立即处理、稍后处理和仅知会的事项。
- 对重复通知进行合并。
- 支持安静时段和通知频率控制。
- 支持按任务和渠道设置通知偏好。
- 支持待审批事项直接转化为用户操作。
- 支持任务完成后的结构化交付。
- 支持多渠道之间的通知状态同步。
- 支持通知失败重试和升级。
- 支持用户反馈通知是否有价值。
- 防止多个 Worker 分别向用户发送重复信息。

---

## 5.15 观测、评估与运营控制模块

### 模块职责

使系统行为可解释、可测试、可评估和可持续优化。

### 必须实现的功能

- 串联事件、路由、任务、模型、工具、审批和交付过程。
- 记录任务状态变化和关键决策依据。
- 记录模型调用的用途、耗时和资源消耗。
- 记录工具调用和外部副作用。
- 支持按任务查看完整运行时间线。
- 支持异常任务重放和问题定位。
- 支持建立主动判断、任务关联和恢复能力的评估集。
- 支持对规则、提示词和模型策略进行版本管理。
- 支持小范围发布和快速回退。
- 支持按用户、任务类型和渠道统计成本与效果。
- 支持将用户纠正转化为后续评估样本。

### 模块边界

- 观测信息不应无边界地暴露敏感内容。
- 内部推理细节不应直接等同于可解释的用户理由。
- 评估样本必须保留来源和适用范围。

## 6. 核心业务流程

## 6.1 用户主动创建任务

1. 用户从任一终端输入目标、想法或材料。
2. Router 判断输入是否属于已有任务。
3. 对新任务建立目标和初步完成标准。
4. Task 管理模块创建任务并持久保存状态。
5. Router 分配合适的 Worker。
6. Worker 加载必要的上下文、个人化规则和工具。
7. Worker 开始执行并持续汇报状态。
8. 需要授权时进入审批中心。
9. 任务完成后进入待验收状态。
10. 用户验收、要求修改或重新打开任务。

## 6.2 跨渠道持续任务

1. 用户在 IM 中提出任务。
2. Worker 订阅对应的 IM Thread。
3. 后续收到相关邮件或文档变更。
4. 新事件首先进入 Router 判断归属。
5. Router 将新 Thread 关联到同一 Task。
6. Worker 获取新要求并更新计划。
7. 后续已归属事件通过订阅直接进入 Worker。
8. Router 向用户汇总任务变化。
9. 最终交付物返回合适的工作渠道。

## 6.3 多任务并行与插话

1. 多个 Worker 分别推进不同任务。
2. 用户在任何时间输入新要求。
3. Router 判断输入对应哪个任务。
4. 对已有任务的补充进入对应 Worker。
5. 对新任务创建新的 Worker。
6. 对停止或修改优先级请求立即更新任务状态。
7. 其他任务保持上下文隔离并继续运行。

## 6.4 主动准备

1. 系统接收到环境事件。
2. 事件中心完成准入和初步分类。
3. Router 判断是否存在值得准备的工作。
4. 主动策略模块评估价值、成本、用户角色和当前任务状态。
5. Worker 只进行无副作用准备。
6. 系统再次检查结果价值。
7. 有价值的结果进入用户收件箱。
8. 需要正式执行时进入审批流程。
9. 无价值结果保持安静或丢弃。

## 6.5 设备离线与恢复

1. 云端任务持续推进。
2. 任务遇到必须访问特定设备的步骤。
3. 系统将任务置为等待设备，并记录缺失能力。
4. 其他不依赖该设备的任务继续执行。
5. 设备上线后重新上报状态和能力。
6. 系统核对等待步骤是否仍然有效。
7. 工具执行前重新检查权限和任务状态。
8. 执行完成后恢复任务主流程。

## 6.6 异常恢复

1. Watchdog 发现无进展、异常循环或外部服务故障。
2. 系统暂停新的外部副作用动作。
3. 读取任务最近检查点。
4. 核对未完成工具调用的真实状态。
5. 选择恢复、重新分派或请求人工接管。
6. 恢复后验证任务是否重新产生实质进展。
7. 将异常和恢复过程写入任务时间线。

## 6.7 用户校准与长期规则更新

1. 用户指出结果不符合预期。
2. Agent 说明当前对目标和约束的理解。
3. 用户指出差异及原因。
4. 系统判断问题来自缺少背景、状态过期、任务理解或长期规则。
5. 优先修正当前任务。
6. 对需要长期生效的内容提出规则或记忆修改建议。
7. 用户确认后再扩大适用范围。
8. 在后续真实任务中验证修改效果。
9. 无效修改可以回退。

## 6.8 反思模式

1. 用户主动发起反思，或系统在低频策略下准备反思任务。
2. 系统汇集近期工作、当前关注、未完成问题和相关外部材料。
3. Worker 寻找事项之间的关联、矛盾和未验证前提。
4. 输出少量观察及对应依据。
5. 用户选择值得继续讨论的问题。
6. 讨论结果保留推导过程和用户反馈。
7. 未确认内容保持待讨论状态，不自动成为长期结论。

---

## 7. 并发与共享状态要求

- 同一 Task 默认只有一个主写入 Worker。
- 同一共享资源的修改必须能够识别冲突。
- 多 Worker 订阅同一 Thread 时，应避免重复响应用户。
- 共享文件和共享记忆的写入必须保留来源。
- 写入前应检查所依据的状态是否已经过期。
- 关键共享状态需要支持版本比较和冲突处理。
- 未确认推断不能因被多次读取而自动升级成事实。
- 任务取消后，尚未执行的工具动作必须失效。
- 任务恢复后，不应使用已经过期的授权。

---

## 8. 非功能需求

### 8.1 性能与响应

- 普通用户输入应及时被系统接收并反馈任务归属状态。
- 长工具调用不得阻塞新的用户输入。
- 高优先级停止和审批请求应优先于普通后台工作。
- Router 应支持事件积压时的批量处理。
- 大量历史资料不应全部进入默认上下文。

### 8.2 可靠性

- 任务状态必须能够独立恢复。
- 外部动作必须考虑超时和结果不确定。
- 重复事件不得导致重复任务或重复副作用。
- 设备和渠道断连不应导致任务状态丢失。
- 恢复失败必须明确呈现，不能伪装成正常完成。

### 8.3 安全与隐私

- 默认采用最小权限。
- 默认减少敏感信息进入模型上下文。
- 默认不允许未经审批的外部写入。
- 默认不将未确认讨论写入长期事实。
- 用户应能撤销设备、渠道、工具和授权。
- 审计记录本身也应受到访问控制。

### 8.4 可维护性

- 渠道、工具、模型和任务策略应保持可替换。
- 模块之间通过明确职责协作，避免共享隐含状态。
- 任务状态和模型上下文应分别演进。
- 主动策略和个人化规则应支持版本化与回退。
- 新增任务类型不应要求修改所有基础模块。

### 8.5 成本控制

- 支持按用户、任务和工具设置预算。
- 支持主动准备的独立预算。
- 支持低价值事件在进入模型前被过滤。
- 支持根据任务类型选择不同能力的模型。
- 支持在达到预算后暂停、降级或请求用户决定。

---

## 9. 分阶段开发范围

## 9.1 第一阶段：连续且可控的任务系统

### 建设目标

验证用户能够创建一个任务、持续推进、随时插话、完成审批并跨入口接续。

### 必须交付

- 统一对话入口。
- 任务中心。
- Task 生命周期管理。
- 单用户逻辑 Router。
- Worker 隔离执行。
- 异步工具执行与停止。
- Live State 和交付物保存。
- 基础渠道接入。
- 基础端侧执行环境。
- 外部写入审批。
- 任务时间线和运行日志。
- 人工暂停、接管与恢复。

### 第一阶段限制

- 仅开放读取、分析、草稿和少量可逆写入。
- 不开放高敏感操作。
- 不默认启用复杂主动策略。
- 不建设 Worker 之间自由通信。
- 不自动将普通讨论写入长期记忆。

## 9.2 第二阶段：主动与跨设备

### 建设目标

验证 Agent 能在低打扰的前提下主动准备，并在多设备环境中持续工作。

### 新增功能

- 更多邮件、日程和 IM 渠道。
- 两级事件过滤。
- Thread 订阅直通。
- 主动策略与投机准备。
- 多设备能力管理。
- 等待设备和离线恢复。
- 记忆中心。
- 来源与确认状态管理。
- 反思模式。
- 主动策略和任务关联评估集。

## 9.3 第三阶段：规模化协作

### 建设目标

在明确权限边界的前提下支持更复杂的任务协作和能力复用。

### 新增功能

- 更复杂的多 Worker 协作。
- 领域专用 Worker。
- 个人 Agent 与团队 Agent 的受控协作。
- 能力分享和反馈回流。
- 更细粒度的成本与模型策略。
- Router 扩展和跨实例协作。
- 组织级权限和共享边界。

---

## 10. 测试要求

### 10.1 模块测试

- 验证各模块的核心状态和边界条件。
- 验证重复输入、空输入、异常输入和权限不足。
- 验证任务暂停、取消、超时和恢复。
- 验证记忆确认、修改、作废和删除。
- 验证授权到期和撤销。

### 10.2 模块协作测试

- 验证事件到任务、任务到 Worker、Worker 到交付的完整链路。
- 验证渠道输出和通知状态一致。
- 验证审批通过前后工具行为不同。
- 验证设备离线时任务进入正确等待状态。
- 验证 Router 与 Worker 的状态汇报一致。

### 10.3 故障注入测试

- 模型调用超时。
- 工具调用超时。
- 外部动作结果不确定。
- 事件重复推送。
- 渠道断连。
- 设备离线。
- 状态保存失败。
- Worker 异常退出。
- Watchdog 自身不可用。

### 10.4 安全测试

- 外部内容包含诱导性指令。
- 低权限事件尝试触发高权限工具。
- 尝试让凭据进入模型上下文。
- 已撤销设备继续接收命令。
- 已取消任务继续执行外部动作。
- 多 Worker 同时修改共享资源。
- 未确认推断被写成长期记忆。

### 10.5 智能体效果评估

- 新旧任务关联准确率。
- 主动事项接受率。
- 无关通知率。
- 应等待事项的错误介入率。
- 用户纠正后的同类问题复发率。
- 恢复后继续执行的正确率。
- 重复外部副作用次数。
- 交付物一次验收通过率。

## 11. 验收标准

| 能力 | 验收标准 |
|---|---|
| 连续交互 | 用户可以从不同入口继续同一任务，无需重复完整背景 |
| 任务关联 | 新渠道事件能够正确关联已有任务，不确定时会请求澄清 |
| 多任务并行 | 一个任务执行期间可以创建和推进其他任务，上下文不串扰 |
| 异步插话 | 长工具执行期间可以补充要求、调整优先级或停止任务 |
| 主动准备 | 能够提前生成有价值的草稿，低价值结果不会打扰用户 |
| 主动边界 | 已有他人负责或只需等待的事项不会被错误接管 |
| 审批控制 | 需要审批的外部动作未经批准不能执行 |
| 状态接续 | 新 Worker 或另一设备能够根据 Live State 接续任务 |
| 异常恢复 | 恢复前会核对工具结果，不重复产生外部副作用 |
| 记忆治理 | 用户能查看来源、确认状态并修改或删除记忆 |
| 设备控制 | 设备撤销后不能继续接受新的执行命令 |
| 交付验收 | 用户能够区分草稿、待验收和正式交付版本 |
| 运行透明 | 能按任务追踪事件、决策、工具、审批和异常恢复过程 |
| 成本控制 | 达到任务或主动准备预算后能够暂停或请求用户决定 |

## 12. 核心运营指标

### 连续性

- 跨渠道任务关联成功率。
- 用户重复补充背景的次数。
- 跨设备任务接续成功率。

### 效率

- 任务完成时间分布。
- 用户插话后的响应时间。
- 并行任务上下文串扰率。
- 交付物一次验收通过率。

### 主动性

- 主动事项接受率。
- 无关通知率。
- 应关注事件漏报率。
- 应等待事项错误介入率。
- 投机准备有效产出率。

### 可靠性

- 异常自动恢复成功率。
- 恢复后任务完成率。
- 重复外部副作用次数。
- 设备离线恢复成功率。

### 可控性

- 未授权外部副作用次数。
- 审批撤销和停止操作生效情况。
- 记忆来源可追溯率。
- 用户纠正后的复发率。

### 成本

- 单个完成任务的综合成本。
- Router 决策成本占比。
- 无效主动准备成本。
- 工具和模型调用预算超限情况。

## 13. 主要风险与应对

| 风险 | 表现 | 应对方向 |
|---|---|---|
| 任务误关联 | 新事件更新到错误任务 | 置信判断、用户澄清、关联历史可撤销 |
| 上下文污染 | 不相关任务或旧重点影响当前判断 | Worker 隔离、按需召回、默认注入控制 |
| 记忆污染 | 推断被当成事实反复使用 | 来源、确认状态、用户验收、作废机制 |
| 主动打扰 | 频繁通知或接管他人工作 | 角色判断、静默策略、通知反馈 |
| 提示词注入 | 外部内容诱导执行危险动作 | 信任分级、权限隔离、动作审批 |
| 凭据泄露 | 敏感信息进入上下文或输出 | 凭据代理、最小读取、输出检查 |
| 重复副作用 | 故障恢复后重复发送或修改 | 状态核对、幂等控制、恢复前暂停 |
| 共享写入冲突 | 多 Worker 覆盖文件或记忆 | 单一主写、版本比较、冲突处理 |
| Router 瓶颈 | 所有事件等待全局判断 | 程序过滤、订阅直通、批处理 |
| 成本失控 | 主动准备和多 Worker 消耗过高 | 独立预算、价值评估、停止条件 |

---

## 14. 需要在开发过程中持续决策的问题

- 任务关联在何种置信程度下可以自动执行。
- 哪些动作可以从逐次审批逐步升级为任务范围授权。
- 不同记忆的默认保留期限和重新确认方式。
- 用户临时纠正何时可以转化为长期规则。
- 个人 Agent 与团队 Agent 共享哪些上下文和交付物。
- 多 Worker 何时需要直接协同，何时必须由 Router 中转。
- Watchdog 可以自动执行哪些恢复动作。
- 如何向用户展示足够但不过量的运行细节。
- 如何评估主动行为的真实价值，而不是只统计处理数量。
- 如何防止系统为了维持活跃而制造不必要任务。

## 15. 首个完整迭代建议

首个完整迭代应打通以下闭环：

1. 用户从终端或 IM 创建任务。
2. Router 建立 Task 并分配 Worker。
3. Worker 读取必要资料并生成草稿或分析结果。
4. 用户可以在执行过程中插话、修改要求和停止任务。
5. 外部写入动作进入审批中心。
6. 任务进展写入 Live State。
7. 交付物进入任务中心等待验收。
8. 用户可以从另一入口继续查看和处理同一任务。
9. 异常后能够恢复或明确转入人工处理。
10. 全过程可以追踪和评估。

这一迭代优先证明三件事：

- 任务可以持续推进。
- 用户可以随时控制。
- 系统异常后不会失去状态或重复产生副作用。

主动策略、复杂长期记忆和多 Agent 协作应建立在这一闭环稳定运行之后。
