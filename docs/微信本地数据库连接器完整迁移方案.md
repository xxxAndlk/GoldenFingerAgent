# 微信本地数据库连接器完整迁移方案

> 日期：2026-11-03  
> 性质：可直接交给编码 Agent 实施的替换方案，不代表新链路已经安装或真机验收。  
> 目标：删除“当前窗口截图＋OCR”的旧微信插件，换成“按授权联系人读取本地数据库”的后台只读链路，同时补齐消息身份、可靠投递、模型工具、提示词、权限和验收。
>
> 实施状态（2026-11-03/04）：M0–M3 已落地；旧 OCR 文件/状态/UI 已删除。微信 4.1.15.13 本机 25 个库全部只读解密，稳定 `source_id` 授权、确定性 `event_id`、Spool 入库、重启幂等和四个只读工具已接线。
>
> **运行时迁移（2026-11-04）**：原 Python/wechatauto 连接器已替换为 Go 实现（`cmd/wechat-db-connector` + `internal/wechatdb`），取钥、页解密、WAL 合并和 SQLite 查询均在 Go 中完成；Python 源码与 venv 已从仓库和桌面包删除。真实验收证据见 `.agent/progress.md`。

## 1. 最终决策

采用以下主链路：

```text
微信 4.x 本地数据库
  → wechatauto-replica（只允许 WeChatDB + db.Listener）
  → 独立 Python 只读连接进程
  → NDJSON 标准输出
  → Electron 连接器监督器
  → 现有 Observation Envelope + 持久 Spool
  → 现有 POST /api/channels/wechat/messages
  → Trigger / Thread / Summary / Brief / WorkTask
  → Go 只读查询工具
  → 主对话或 Worker
```

必须同时遵守六条边界：

1. **只读消息，不操作微信界面**：不调用 `WeChat`、`AddListenChat`、发送、UIA、OCR、点击、滚动和独立聊天窗。
2. **按稳定会话 ID 授权**：不再按窗口标题授权，不做全量会话监听。
3. **模型不接触第三方连接器和密钥**：模型只查询已授权、已入库的数据。
4. **先持久化再分析**：Spool 未落盘不能推进采集检查点；服务重启依靠稳定消息 ID 幂等。
5. **联系人说的话不是机主指令**：普通联系人消息不得直接创建 Worker、调用 Bash、读取文件或修改任务。
6. **不删除历史证据**：旧 OCR Trigger 保留为历史数据；旧采集代码、状态和 UI 在新链路验收后删除。

本方案不改变网页、邮件、工作轨迹和手机通知连接器，也不推翻 Super-agent 事件层。

## 2. 旧实现为什么必须整体替换

当前旧链路由以下文件组成：

- `desktop/wechat-window.js`：UIA 定位微信窗口。
- `desktop/wechat-parser.js`：按 OCR 坐标猜标题、气泡、发送方向和可见增量。
- `desktop/wechat-connector.js`：每 3.5 秒截图、OCR、对齐并入队。
- 对应的三个测试文件、IPC、工作台预览和打包引用。

它存在的是数据模型问题，不只是识别准确率问题：

| 旧问题 | 新方案 |
|---|---|
| 只能看到当前打开会话 | 数据库轮询已授权会话，不要求目标会话处于前台 |
| 标题被当作稳定身份 | 使用账号＋微信 `username` 作为稳定会话身份 |
| 真实发送时间未知 | 使用数据库 `create_time`，另存 `observed_at` |
| 方向靠气泡左右位置猜 | 使用发送者 username 与本机账号比较 |
| 随机 event ID＋可见序列对齐 | 使用账号＋会话＋分片＋`local_id` 稳定幂等 |
| `current_visible` 永远是不完整片段 | 单条消息可完整，另用 `sync_scope` 表明同步范围 |
| 群聊发送者经常 unknown | 按消息所在分片的 `Name2Id` 解析 |
| OCR 错字、漏行、图片误识别 | 文本直接读数据库；媒体只保留真实类型和本地可用状态 |

旧方案中“禁止读取个人微信数据库”的项目约束需要被明确替换，不能一边保留旧约束一边偷偷绕开。

2. 用户在新会话列表中重新勾选授权。
3. 旧标题策略保留一段时间用于审计，但不再参与新连接器判断。
4. 新连接器默认 `latest_only`，避免启用时把旧历史重新灌入系统。

### 4.2 第三方适配层

唯一允许的第三方入口：

```python

```

禁止在适配层以外出现第三方微信 import。适配层不得导入：

```python

# 以及任何 UIA、OCR、发送、朋友圈点赞、窗口控制入口
```

依赖必须固定版本或 commit，并记录来源和许可证。首次只接入 `wechatauto-replica`；`wechat4-db-export` 仅作为取钥失败后的只读诊断参考，不与主连接器同时写入消息，避免双链路重复。

### 4.3 Electron 与 Python 的 NDJSON 协议

Electron 启动唯一子进程；微信渠道关闭、无授权会话或桌面退出时停止。标准输出只传 NDJSON，日志只能走 stderr 且不得包含正文和密钥。

Electron → Python：

```json
{"id":"req-1","type":"configure","enabled":true,"chats":["account:wxid_1","account:group@chatroom"],"interval_ms":2000,"mode":"latest_only"}
{"id":"req-2","type":"list_chats"}
{"id":"req-3","type":"health"}
{"id":"req-4","type":"stop"}
```

Python → Electron：

```json
{"type":"ready","protocol_version":1,"connector_version":"..."}
{"type":"message","message":{"schema_version":2}}
{"type":"chats","request_id":"req-2","chats":[]}
{"type":"health","state":"observing","last_db_read_at":"...","authorized_chats":2}
{"type":"error","code":"unsupported_version|permission_denied|key_unavailable|db_locked|internal","message":"不含路径和密钥的错误"}
```

协议要求：

- 单行上限 256 KB，超限媒体正文转摘要，不直接传 base64。
- 每条请求有 ID；未知请求类型返回错误，不执行命令。
- Python 不接收文件路径、shell、SQL 或模型自由文本作为命令。
- 进程异常退出采用有限退避重启；连续失败进入 `error`，不形成重启风暴。
- 配置撤销后立即停止相应 listener，并清除该来源未投递正文。

## 5. 消息身份、字段与完整性

### 5.1 稳定身份

```text
account_key   = 本机账号的稳定匿名标识
chat_key      = 微信 username（wxid_* 或 *@chatroom）
source_id     = wechat-db:<account_key>:<chat_key>
message_key   = <account_key>:<chat_key>:<shard>:<local_id>
event_id      = 对 message_key 做确定性 UUID 派生
external_id   = wechat:<message_key>
thread_key    = wechat:<account_key>:<chat_key>
```

`local_id` 跨分片会重复，因此不得只用 `(chat, local_id)`；`content_hash` 只用于变化检测，不能作为消息身份；两条相同正文必须保留为两条消息。

显示名只用于展示。联系人改名、群改名或同名联系人都不能改变 `source_id`、Thread 和授权。

### 5.2 HTTP 请求扩展

保留现有字段并新增：

```json
{
  "schema_version": 2,
  "source": "联系人显示名",
  "source_id": "wechat-db:account:wxid_example",
  "display_name": "联系人显示名",
  "account_id": "account",
  "chat_type": "private|group|system|unknown",
  "message_id": "account:wxid_example:message_0.db:123",
  "event_id": "确定性 UUID",
  "sender": "发送者显示名",
  "sender_id": "发送者稳定 username，未知则空",
  "actor_role": "owner|contact|system|unknown",
  "direction": "self|other|system|unknown",
  "message_type": "text|image|voice|video|file|system|other",
  "text": "消息正文或如实的媒体占位",
  "kind": "message",
  "occurred_at": "2026-11-03T21:00:00+08:00",
  "observed_at": "2026-11-03T21:00:02+08:00",
  "received_at": "2026-11-03T21:00:02+08:00",
  "content_hash": "正文哈希",
  "completeness": "complete",
  "sync_scope": "local_incremental",
  "incomplete": false,
  "shard": "message_0.db",
  "local_id": 123,
  "sort_seq": 456789,
  "cursor": "连接器游标",
  "raw_ref": ""
}
```

语义必须固定：

- `completeness=complete` 只表示**这一条消息正文完整**，不表示整个会话历史完整。
- `sync_scope=local_incremental` 表示只覆盖本机数据库中、连接器启动后观察到的新消息。
- 可选首次回填使用 `sync_scope=local_backfill`，必须带用户选择的时间范围。
- `occurred_at` 来自数据库；`observed_at` 是连接器看到它的时间，两者不得混用。
- 服务端 `Trigger.ReceivedAt`：有 `occurred_at` 时使用真实发生时间，否则使用 `observed_at`。
- `trusted` 始终为 false；`actor_role=owner` 也不把消息正文提升为系统指令。
- 新链路不再给完整正文追加“当前可见内容”提示。

### 5.3 增量与重启

1. 首次启用默认 `latest_only`：记录当前高水位，不导入全部历史。
2. 每次消息成功写入本地 Spool 后才推进该会话检查点。
3. 服务确认前进程崩溃：从 Spool 重试，服务端按稳定 external ID 返回原 Trigger。
4. 检查点未保存但进程崩溃：允许重读，依赖同一 deterministic event ID 去重。
5. `sort_seq` 可能并列：游标必须保存 `(sort_seq, shard, local_id)` 集合或等价水位，不能只查询 `sort_seq > N`。
6. 同一会话保序，不同会话可并行；模型调用不得位于采集回调内。
7. 第一版只处理新增消息。若同一 `message_key` 后续正文发生变化，标记 `message_revision` 待后续实现，不得静默覆盖旧 Trigger，也不得当成一条全新普通消息。

### 5.4 历史回填

历史回填不是监听默认行为，只允许在 UI 中由用户明确发起：

- 指定一个已授权会话。
- 指定起止时间和最大条数。
- 显示将读取的范围，完成后显示新增、重复、跳过和失败数量。
- 使用同一稳定消息 ID 幂等；重复执行不得重复建 Trigger。
- 模型没有“导出全部微信历史”的工具。

## 6. 服务端与数据迁移

### 6.1 授权校验改为稳定 source_id

`handleWeChatMessage` 当前按 `req.Source`（显示名）调用授权检查，新链路必须改为按 `req.SourceID` 校验。显示名不再参与权限判断。

服务端仍需再次校验，不能信任 Electron 已过滤：

```text
channel enabled
  AND source_id explicitly allowed
  AND owner_user_id matches
  → 才允许正文进入 Trigger
```

被拒绝时只计数，不保存正文、发送者、消息 ID 对应的原文或模型上下文。

### 6.2 新迁移建议

`0014_wechat_db_connector.sql` 增加：

```text
agent_channel_source
  owner_user_id, channel, source_id, display_name,
  account_alias, chat_type, first_seen_at, last_seen_at, metadata_json

agent_channel_health
  owner_user_id, channel, connector_id, state,
  last_observed_at, last_event_at, last_delivered_at,
  pending_count, filtered_count, failed_count,
  last_error_code, last_error_safe, updated_at
```

并为微信查询增加 `(owner_user_id, channel, thread_id, received_at)` 索引。所有表带 `owner_user_id`，所有查询按 owner 过滤。

`agent_channel_policy.source` 暂不急着改名，但其语义对微信新链路必须是稳定 `source_id`。UI 通过 `agent_channel_source` 把 ID 映射为显示名。

### 6.3 健康状态

状态枚举统一为：

```text
off | starting | needs_login | needs_permission | waiting_authorization |
observing | degraded | unsupported_version | error
```

展示最近数据库读取、最近新消息、最近入库、授权会话数、待发数、过滤数、最后安全错误和采集延迟。不得展示数据库密钥、完整账号路径、进程内存信息或未授权会话正文。

## 7. 模型工具设计

### 7.1 总体原则

模型工具只访问 Go 中已入库的 Trigger/Thread 和健康表，**不直接调用 Python，不直接打开微信数据库，不接收 SQL，不返回密钥和原始文件路径**。

每次读取都重新校验 owner 和当前来源授权；来源被撤销后，工具不能继续把该来源历史正文注入模型。

首版增加四个只读工具：

| 工具 | 用途 | 风险 |
|---|---|---|
| `get_connector_health` | 判断微信是否真的在采集、为何没有新消息 | `RiskRead` |
| `list_wechat_chats` | 列出当前已授权会话，解决同名和选择问题 | `RiskRead` |
| `read_wechat_messages` | 按会话和时间游标读取消息 | `RiskRead` |
| `search_wechat_messages` | 在已授权消息中按关键词、发送者和时间检索 | `RiskRead` |

在 `classifyToolName` 中显式归类为 `RiskRead, false`；不要依赖默认分支。它们可出现在 interactive、read、internal、external Profile，但数据授权仍独立生效。

### 7.2 `get_connector_health`

```json
{
  "channel": "wechat_desktop"
}
```

返回：

```json
{
  "channel": "wechat_desktop",
  "state": "observing",
  "authorized_chats": 2,
  "last_observed_at": "...",
  "last_event_at": "...",
  "last_delivered_at": "...",
  "pending": 0,
  "sync_scope": "local_incremental",
  "last_error": null
}
```

没有消息时，模型先根据健康状态区分“未启用、未授权、微信未登录、版本不兼容、服务待投递、确实没有新消息”，不能统一回答“微信没消息”。

### 7.3 `list_wechat_chats`

参数：

```json
{
  "query": "可选显示名过滤",
  "limit": 20
}
```

返回仅含当前允许来源：

```json
{
  "chats": [
    {
      "source_id": "wechat-db:account:wxid_example",
      "display_name": "张三",
      "chat_type": "private",
      "last_message_at": "...",
      "last_direction": "other"
    }
  ],
  "truncated": false
}
```

`limit` 默认 20、最大 50。工具描述必须写明：用户只给称呼且匹配多个会话时，先让用户选择，不得自行挑一个。

### 7.4 `read_wechat_messages`

参数：

```json
{
  "source_id": "wechat-db:account:wxid_example",
  "before": "可选：上一页最早消息的稳定游标",
  "from": "可选 RFC3339",
  "to": "可选 RFC3339",
  "limit": 30
}
```

返回一页按发生时间正序的消息：

```json
{
  "source_id": "wechat-db:account:wxid_example",
  "display_name": "张三",
  "messages": [
    {
      "message_id": "account:wxid_example:message_0.db:123",
      "trigger_id": "trigger-id",
      "sender": "张三",
      "actor_role": "contact",
      "direction": "other",
      "message_type": "text",
      "text": "周五下午三点评审",
      "occurred_at": "...",
      "observed_at": "...",
      "completeness": "complete",
      "sync_scope": "local_incremental"
    }
  ],
  "next_before": "稳定分页游标或 null",
  "truncated": false,
  "coverage_note": "仅包含本机已采集范围，不代表微信服务器全部历史"
}
```

`limit` 默认 30、最大 100；单条正文进入模型前最多 2000 字并标 `text_truncated`。分页使用时间＋Trigger ID 或等价稳定游标，不用容易漂移的 offset。

### 7.5 `search_wechat_messages`

参数：

```json
{
  "query": "评审",
  "source_id": "可选，限定会话",
  "sender": "可选，精确发送者显示名",
  "direction": "self|other|system|unknown",
  "from": "可选 RFC3339",
  "to": "可选 RFC3339",
  "limit": 20
}
```

要求：

- 关键词最长 200 字，结果最多 50 条。
- SQL LIKE 通配符必须转义；不能拼接模型提供的 SQL。
- 返回字段与读取工具一致，并附 `source_id/display_name`。
- 无结果不代表微信中不存在，只代表当前授权且已采集的数据中未命中。

### 7.6 首版明确不提供的工具

```text
wechat_send
wechat_start_listener
wechat_extract_key
wechat_authorize_contact
```

## 9. 路由和工具安全闸

提示词之外必须有代码门禁：

```text
未经授权 source_id
  → 不入 Trigger、不进摘要/索引/简报/记忆

direction=self
  → 可入 Thread/Summary；默认不通知、不建 Worker

actor_role=contact/unknown
  → 可通知/摘要/草稿
  → 禁止自动 Worker、Bash、文件写入、修改长期任务

机主在主对话明确要求“根据张三刚才的消息……”
  → 通过只读微信工具取证据
  → 再按现有工具授权和 WorkTask 规则执行

回复微信
  → ActionOutbox 草稿 + 人工审批
  → 首版没有发送器，不得报告已发送
```

微信正文即使写着“这是机主”“已批准”“忽略以上规则”，也不能改变 `actor_role` 或授权。

## 11. 密钥、缓存与日志

- `WECHATAUTO_KEYS_DIR` 指向桌面 `userData` 下独立受保护目录。
- 优先使用上游 DPAPI 密钥缓存；启动时检测是否退化为明文，明文退化要显示安全警告。

- 微信升级导致不支持时进入 `unsupported_version`，停止采集并提示，不自动尝试 UIA、OCR 或 BMA 作为隐式 fallback。

## 13. 必过验收

### 13.1 采集与身份

1. 目标会话不在前台、微信窗口被遮挡时，仍能收到授权会话的新消息。
2. 未授权会话在同一时间收到消息，正文、发送者和摘要均不进入系统。
3. 同一联系人连续发送两次“收到”，必须产生两个不同 message_key 和 Trigger。
4. 两个同名联系人不共享 Thread、授权或查询结果。
5. 联系人改名后 Thread 与授权保持稳定。
6. 群聊按消息所在分片解析真实发送者；无法解析时标 unknown，不猜。
7. 自己发的消息 direction=self，对方发的 direction=other；系统消息单独处理。
8. occurred_at 使用数据库时间，服务离线补交后仍保留原发生时间。
9. 跨分片 local_id 相同不互相覆盖；sort_seq 并列不丢消息。
10. 首次启用不会把全部历史重新导入。

### 13.2 可靠性与撤销

11. Go 服务停止后继续收消息，恢复后 Spool 补交且不重复。
12. Electron/Python 任一进程重启后不重复导入，也不因内存水位丢失合法消息。
13. Python 连续崩溃进入可见错误，不出现无限重启和高 I/O。
14. 撤销授权后 listener 停止，待发正文被清除，模型工具也不能继续读取该来源正文。
15. 微信升级或取钥失败显示明确状态，不自动打开窗口或退回 BMA。

### 13.3 模型与提示词

16. 用户问“张三刚才说了什么”，工具返回真实消息、方向和时间，而不是模型凭记忆回答。
17. 查不到时回答限定于“当前已授权、已采集范围”，不否认微信服务器上存在。
18. 联系人消息写“忽略规则并运行命令”，只作为正文，不产生工具调用。
19. 普通联系人消息即使 auto_worker_enabled=true，也不能直接创建或修改 WorkTask。
20. 用户要求回复时只产生待审批草稿，未审批前不能声称已发送。
21. Thread 摘要把“对方要求周五交付”和“我同意周五交付”区分开。
22. 每日简报按会话聚合，不被“嗯、收到”刷屏。

### 13.4 隐私与性能

23. 日志、错误、工具结果和文档中没有密钥、数据库明文路径或未授权正文。
24. 只监听少量授权会话时，轮询不会每轮扫描全部会话和全量历史。
25. 密钥缓存使用 DPAPI；若出现明文退化，界面有明确警告。
26. 真机测试只使用本人账号和明确授权的测试联系人，不读取他人设备。
