# 三端拆分：电脑工作助手 / 手机生活管家 / 中继

最后更新：2026-10-30

本文件定义改造目标与边界。行为判断仍以代码和 `.agent/AGENT.md` 为准。

## 1. 目标形态

| 端 | 定位 | 运行内容 |
|---|---|---|
| 电脑端 | **工作助手** | Go 服务 + Electron：CLI/桌面/A2A/BMA 调度、工作轨迹、文件与命令工具、异步任务 |
| 手机端 | **生活管家** | Go 服务（gomobile 或独立进程）+ 极薄 Kotlin 能力层：语音口令、情景记忆、提醒、通知中心、无障碍操控 |
| 中继 | **只转发** | `cmd/relay`：配对、鉴权、投递。不执行任务、不持久化业务数据，可跑在 2C2G |

互通方向（当前范围）：

```
手机生活管家 --command--> 中继 --command--> 电脑工作助手（执行）
手机生活管家 <--result--- 中继 <--result--- 电脑工作助手（回传同一次请求的结果）
```

电脑端**主动发起**到手机（推送、远程唤起手机）暂不实现。手机发起的请求必须能拿到结果，否则该方向没有意义。

## 2. 为什么手机端不能"纯 Go、不要安卓代码"

Android 的能力边界是 Binder/framework API，只在 APK 内由 Java/Kotlin 实现并写进 Manifest 才存在：

| 能力 | 依赖 |
|---|---|
| 看屏幕 / 点击 / 手势 / 截图 | `AccessibilityService` |
| 读通知 | `NotificationListenerService` |
| 口令唤醒 / 语音识别 / 播报 | `SpeechRecognizer` / `TextToSpeech`（或云 ASR+TTS，但录音仍需 `AudioRecord`） |
| 常驻、开机自启、Doze 唤醒 | `Service`+`startForeground`、`BOOT_COMPLETED`、`WorkManager` |
| 悬浮条 / 确认弹窗 / 急停 | `SYSTEM_ALERT_WINDOW` |
| 界面与运行时权限 | `WebView`、`Activity` |

旁路都不成立：无线 ADB 需开发者选项常开并每次配对；Shizuku 仍需第三方 App 且调用端是 Java；Termux 纯 Go 二进制拿不到无障碍与通知权限。

因此目标不是"去掉安卓代码"，而是**把业务逻辑搬进 Go，把 Kotlin 压成无判断的能力层**。

### 2.1 现状偏差（需要搬回 Go 的部分）

| Kotlin 文件 | 现存业务逻辑 | 目标 |
|---|---|---|
| `accessibility/SafetyGuard.kt` | 敏感词/敏感包名判定、人工确认、急停 | 判定搬 Go（`device.Guard`）；Kotlin 只留确认条 UI 与本地急停计时器（断网也必须能停） |
| `memory/MemoryCaptureService.kt` | 口令解析、10s 指令窗、4s 合并 / 30s 上下文窗、chat 与 capture 的分流 | **已搬 Go**（`internal/voice` + `POST /api/voice/text`）：Kotlin 只上报 ASR 文本并执行返回的动作 |
| `notify/InboxApi.kt` | 用 pkg+title+text 反查 `event_id` 再 snooze | 搬 Go：`/api/inbox/snooze` 支持内容匹配 |
| `NotifyPoller.kt`、`Executor.kt`、`NodeDumper.kt`、`OverlayManager.kt` | 通知渲染、动作执行、节点序列化、悬浮 UI | 保留，属于能力层 |

## 3. 中继协议（已实现）

代码：`internal/relay`（状态机 + HTTP/WS + 电脑端客户端）、`cmd/relay`（二进制）。

### 3.1 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/v1/desktop/register` | 电脑首次登记，返回 `desktop_id` + `desktop_token`（本地落 `relay.json`，0600） |
| POST | `/v1/pair/code` | 电脑（凭 desktop 凭据）生成 6 位一次性配对码，默认 5 分钟有效 |
| POST | `/v1/pair` | 手机凭配对码换取 `channel_id` + `phone_token` |
| GET | `/v1/channels` | 列出已配对手机 |
| DELETE | `/v1/channels/{id}` | 解除绑定（手机需重新配对） |
| GET | `/v1/ws?role=desktop\|phone&id=…&token=…` | 长连接；token 支持 `X-Token` 头 |
| GET | `/healthz` | 存活与容量计数（不含消息内容） |

### 3.2 报文

```json
{"v":1,"id":"m-…","kind":"command","channel":"…","from":"phone:…","to":"desktop:…","ts":1760000000000,"reply_to":"","payload":{"text":"把下载目录按类型整理"}}
```

- `kind`：`hello` / `command` / `result` / `ack` / `error` / `ping` / `pong`
- `channel`、`from`、`to` 由中继**盖章**，客户端自填一律被覆盖或拒绝。
- 电脑端的 `result` 必须回带命令里的 `channel`，中继校验该通道属于本机，否则拒绝（已测）。
- 同一 `id` 只投递一次（中继 10 分钟窗口），电脑端再按 `id` 去重，保证"至少一次投递、最多一次执行"。

### 3.3 离线与容量

- 手机先发、电脑不在线：消息入内存队列，回执 `{"status":"accepted","queued":true}`。
- 每通道每方向默认 200 条、TTL 24 小时；超限丢最旧并计数。
- 中继不落盘：重启即丢未投递消息。业务状态（任务、通知、幂等键）始终在电脑端 SQLite。

### 3.4 安全

- 配对码 6 位、5 分钟一次性；`/v1/pair` 按 IP 限流 10 次/分钟，`/v1/pair/code` 30 次/分钟，`/v1/desktop/register` 20 次/分钟。
- 通道隔离：用 `desktop_token` / `phone_token` 鉴权，无法跨通道读写。
- 上线必须 TLS（`https://` / `wss://`），否则配对码与消息内容在链路上明文。
- 电脑端的 `/api/relay/*` 只允许 127.0.0.1 访问（本机界面获取配对码），本机服务没有鉴权，不能把这些接口暴露到局域网。

## 5. Python 记忆服务 → Go（2026-10-30 已完成主体）

原先 `memory_service/app.py` 是 Graphiti + Kuzu 封装，`internal/memory/graphiti.go` 是它的 HTTP 客户端。现已改为内置 Go 实现，**不引入图数据库、不新增任何依赖**（FTS5 虽然可用但不支持中文分词，所以关键词匹配在 Go 内打分）。

| 文件 | 作用 |
|---|---|
| `migrations/0006_longterm_memory.sql` | `mem_episode`（`source_id` 主键即幂等键，带抽取状态/重试计数）+ `mem_edge`（主体/关系/客体、`valid_from`/`valid_to`、`source_refs`） |
| `internal/store/longterm.go` | 片段与事实的仓储：幂等写入、待抽取队列、按三元组查活动事实、时间失效、按来源删除、硬删除 |
| `internal/memory/extract.go` | 抽取提示词与 JSON 解析；原文用 `<<<DATA … DATA>>>` 包裹并声明“是数据不是指令” |
| `internal/memory/native.go` | `LongTermMemory` 实现：Append 幂等落库 + 唤醒后台；RunOnce/Start 抽取；Search 向量+关键词+时效融合并做一跳主体扩展；Forget 真删；Health |

行为约定：

- 抽取失败不阻塞聊天：原文先落库，失败重试 3 次后标 `failed` 并保留原文。
- 同一 (主体, 关系) 的新值把旧值标 `valid_to`，**不覆盖**；普通查询不给历史，问“以前”才返回失效事实。
- 同一事实重复出现只补充 `source_refs`，不产生重复条目。
- 遗忘：`ForgetPerson`/`ForgetFact` 现在会同步调用长期记忆的 `Forget` 真删（Graphiti 阶段这里是 `ErrUnsupported`，从未生效）。
- 只能使用内置实现：Python 服务、`internal/memory/graphiti.go`、`desktop/memory-manager.js` 与 `.venv-memory` 已于 2026-10-30 全部删除。排障时用 `GFA_MEMORY_DISABLE=1` 退回纯 SQLite 检索。

验证：`internal/memory/native_test.go`（幂等、注入防护、时间失效与历史查询、重复事实只加来源、一跳扩展与无关主体隔离、按来源/事实遗忘、失败重试后标 failed、无向量时关键词降级、owner 隔离）；`internal/store/longterm_test.go`（旧库 0001-0004 → 0006 升级、仓储往返与引用删除）；`cmd/server` 与 `android/gosvc` 均已编译通过。

未验证：真实模型下的抽取质量。

### 5.1 历史图谱的收尾（2026-10-30）

Graphiti/Kuzu 的数据不是 SQLite 的替代品，而是「LLM 抽取出来的实体与关系」这一层派生物，Kuzu 又是私有文件格式，删掉 Python 环境就再也读不出来。因此按「先导出、后删除」处理：

1. `scripts/export-graphiti-kuzu.py`（只读打开）把 `Episodic` / `Entity` / `RelatesToNode_`（Graphiti 采用「边当节点」，事实文本在这一层）连同 `RELATES_TO` 还原出的 src/dst 一起导出为开放 JSON。
2. 实际导出结果：**56 段情景、132 个实体、185 条事实**（其中 20 条已 `invalid_at`），落盘 `data/graphiti-export-20261030.json`（568KB，UTF-8）。`Saga`/`Community` 为空。
3. 删除 `memory_service/`、`.venv-memory`（236MB）、`data/graphiti`（81MB）、`data/models`（161MB，Python embedder 的 HF 缓存）、`data/graphiti-verification*`（64MB）与 `data/backups/graphiti-*`（1.1GB 检查点）。`data/` 由 1.4GB 降到 **6.3MB**。
4. 源码与图谱仍留冷备：`.archive/legacy-graphiti-python-20261030.tar.gz`（36KB）、`.archive/graphiti-kuzu-20261030.tar.gz`（3.1MB）。`.archive/`、`data/`、`artifacts/` 已加入 `.gitignore`（含用户私人转写文本，不能入库）。
5. 未做：把导出 JSON 回填进 `mem_episode`/`mem_edge`。这需要写 `cmd/import-graphiti`（读 JSON → 幂等写入），且会写用户真实数据库，属于单独改动。

| `artifact_accept` / `artifact_reject` | `POST /api/artifacts/{id}/…` | 必有 | **高** |
| `brief_latest` / `brief_list` / `brief_get` | `GET /api/briefs*` | 查询 | 只读 |
| `brief_generate` | `POST /api/briefs/generate` | 必有 | 中（生成耗时） |
| `collection_list` / `collection_configure` | `GET/POST /api/collection/channels` | 查询/必有 | 中 |

`conversation_list` 与 `conversation_read` 都必须带 `device_id`（电脑侧落到 `X-Device-Id`）：
未读数按设备统计，列表与已读用不同的设备键会导致角标永远清不掉（有测试）。

### 7.2 结果分类（电脑 → 手机）

`ResultPayload.command` 只能是下面五种之一，**不允许**把「不确定」说成「成功」：

| 值 | 触发条件 | 手机行为 |
|---|---|---|
| `executed` | 电脑返回 2xx | 如实显示结果 |
| `conflict` | 409（版本过期） | 显示真实原因，不排队、不重试 |
| `rejected` | 其余 4xx（电脑明确拒绝） | 显示真实原因，不排队 |
| `queued` | 中继回执 `queued=true`（电脑离线） | 低风险才排队；高风险如实报「需电脑在线」 |
| `unknown` | 超时、5xx、连接中断 | **不排队、不自动重放**，让用户核对 |

### 7.3 重试与「最多一次执行」

- 手机每次投递都生成**新的信封 ID**，但 `payload.idempotency_key` 保持不变。
  信封 ID 不变会被中继当重复丢掉，手机就永远拿不到结果。
- 电脑端 `relay.Client` 有三层保护：
  1. 本进程内同一条幂等键**并发重投**会等第一次的结果，不会执行第二遍；
  2. 内存里保存最近结果的回执（限 4096 条）；
  3. 配置了 `CommandLedger` 时落 SQLite：`done` 直接回放原结果，
     只有 `running` 没有结果的记录按 `unknown` 回执（上次执行被中断）。
- 执行前必须先写 `running` 回执。`Begin` 写失败时**不执行**业务处理器，
  回 `unknown` 并提示核对——没有回执的执行在重启后无法识别，会破坏「最多一次」。
- 回执**读取**失败同样回 `unknown`，但这次结果不能缓存；
  否则一次短暂的数据库故障会把该幂等键永久钉死。
- 手机 BFF 的离线队列（`remote_pending_command`）只在**明确离线**时入队；
  排队时把 `expected_version` 一起存下来，重放时原样带回，不绕过 CAS 检查。
- **重放阶段**遇到超时、5xx、连接中断等非离线错误时标记 `failed`，不再自动重试；
  只有仍然明确离线才保留 pending，等下一次恢复。
- 同一幂等键重复入队时按真实状态返回：同内容且 `pending` → 202 排队中；
  `done` → 200 回放原结果；`failed` → 502 要求核对；同键不同内容 → 409。
- Artifact 交付与离线队列共用同一个幂等键，首次调用和重放走同一条电脑端回执。
- 审批、验收、生成简报**不允许**离线排队：必须等电脑在线拿到真实结果。

### 7.4 手机主对话与电脑事实源的边界

- `GET /api/conversations?kind=main|worker|delegated` 是统一投影；
  旧 `/api/sessions` 语义不变，仍只返回用户可见的普通会话（不含 worker/router）。
- `source_device` 是**会话事实源设备**，不是发起请求的设备。
- 手机主对话读本机投影（手机自己的聊天），Worker/委派/任务读电脑（经 `/api/remote/*`）。
- Worker 会话里的输入一律经 `work_task_message` 进入任务 Inbox；
  桌面端打开 Worker 会话时**不改**主聊天会话指针（`chatSessionId`）。
- `completed` / `cancelled` 是终态：`can_message=false`，前端禁用输入，
  后端 `AddMessage` 也拒绝（要先用 `reopen`）。
- 每日简报的「已读」按设备记在本机，不等于 `delivered`；电脑离线时禁用生成按钮，
  手机侧生成超时（150s）必须长于电脑侧（90s），否则会出现「手机报失败、电脑随后成功」。

## 8. 当前未验证项

- 中继只在 `httptest` 内验证（含 WS 往返、离线队列、去重、越权拒绝、限流、凭据持久化）。
- 未在真实 2C2G 服务器 + TLS 反代下压测；未做长时间断线重连观测。
- 电脑端 `/api/chat` 的实机回环调用未在打包版桌面程序里跑通（需要模型 Key）。
- 手机侧中继客户端、语音判定、异步任务都只有单测与本地回环验证，**未在任何真机上跑过**。
- `MemoryCaptureService` 已瘦身为能力层（见 6.3），但真机的听写稳定性、各 ROM 保活、TTS 与识别互相打断仍未验证。
