# Super-agent 个人 Agent 架构改造计划书补丁

| 项目 | 内容 |
|---|---|
| 日期 | 2026-11-01 |
| 适用 | 《SuperAgent个人Agent架构改造计划书》v0.2 及后续版本 |
| 优先级 | 本补丁与原计划冲突时，以本补丁为准 |

## 1. 产品定位：单用户、单大脑、唯一主会话

本项目是单用户个人助手，不建设多用户、多租户或团队协作系统。

- 只有一个用户、一个身份、一个活跃大脑。
- 不提供用户切换、用户列表或跨用户管理。
- 数据库现有 `owner_user_id` 仅为兼容字段，可在内部绑定固定本地用户，不代表产品支持多用户。
- 客户端不再依赖手动传入 `X-User-Id` 选择身份；服务端在内部确定唯一本地用户。
- 安全重点是本机访问凭证、手机配对和设备权限，而不是多租户权限体系。
- 电脑和手机是同一个主会话的两个视图，不各自形成主聊天记录。

原计划中过重的 owner/token/scope 多用户设计，收缩为“单用户身份 + 配对设备鉴权 + 必要动作权限”。

## 2. DSH 核心吸收点：Session 下沉，主会话统一

底层允许多个 Session 并行，但用户始终只面对一个 Agent、一个主会话。

```text
                      唯一主会话
               电脑端和手机端共享同一视图
                           │
                           ▼
                  常驻 Router / 全局状态
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
      Worker A          Worker B          Worker C
      隐藏会话          隐藏会话          隐藏会话
          └────────────────┼────────────────┘
                           ▼
              结果、经验、未决事项回到统一记忆
```

- Router Session、Worker Session 都是实现细节，不让用户选择或管理。
- Thread 是后台上下文组织方式，不是新的用户聊天窗口。
- 邮件串、微信群、工作片段和项目讨论可以有独立 Thread，但不形成面向用户的独立助手。
- 任务、澄清和审批优先以卡片回到主会话；工作台只是辅助查看入口，不是另一个交互中心。
- 主会话在视觉上长期连续，但底层 Router 仍可压缩、重建和按需召回，不等于维护一个无限增长的 LLM 上下文。

## 3. 内部 Thread 与 Worker 的使用边界

不是每个应用永久运行一个 LLM Session，而是“事项持续保存为 Thread，需要时才运行 Worker”。

| 组件 | 使用方式 |
|---|---|
| Connector/Collector | 确定性采集、过滤、去重，不需要 LLM Session |
| Thread | 持续保存邮件串、微信群、工作片段等上下文 |
| Thread Summary Worker | 新事件累积后做增量总结；同一 Thread 串行更新 |
| Daily Digest Worker | 按日期和游标合并当天摘要，形成跨渠道简报 |
| Action Worker | 执行查资料、起草回复、处理任务等具体工作 |
| Router | 唯一面向用户的交互和全局协调入口 |

所有 Worker 都不直接对用户聊天，只把结果、证据和待决事项交给 Router。

## 4. 每日总结的统一链路

```text
工作轨迹 / 邮件 / 微信 / 日历
              │
              ▼
     确定性采集、过滤、去重、分段
              │
              ▼
       各自 Thread 原始记录
              │
       ┌──────┴────────┐
       ▼               ▼
Thread 总结 Worker   行动 Worker
增量总结、提取事项    查资料、写草稿、执行任务
       └──────┬────────┘
              ▼
       跨渠道每日总结 Worker
              │
              ▼
         常驻 Router
              │
              ▼
          唯一主会话
```

每日总结不是“工作总结 + 邮件总结 + 微信总结”的简单拼接，而应围绕同一事项合并：

- 今天发生了什么重要变化；
- 用户或相关人员做了什么决定；
- 哪些事项已完成、仍在推进或受到阻塞；
- 哪些事项需要用户处理；
- 下一步建议是什么；
- 每个结论对应的来源 Thread、事件和证据 ID。

晚到的事件可以产生简报新版本，但不能悄悄修改已经交付的简报；主会话应提示“简报有更新”。

## 5. 存储、RAG 与注入不是二选一

统一采用：

> 原始信息先存储，摘要作为派生数据，RAG 负责按需找回，最后只把当前任务需要的内容注入模型。

### 5.1 数据分层

| 层 | 保存内容 | 用途 |
|---|---|---|
| 原始层 | 邮件、微信、工作轨迹、时间和来源 ID | 证据、重放、重新总结 |
| Thread 层 | 最近事件、滚动摘要、摘要游标 | 保持事项连续性 |
| 索引层 | 脱敏正文和摘要的结构化/关键词/向量索引 | 按需检索 |
| 摘要层 | 工作片段摘要、每日简报、任务结果和经验 | 低成本默认上下文 |

原始记录是事实依据，摘要不能替代原始记录。摘要必须带来源 ID、覆盖时间和摘要游标。

### 5.2 什么时候使用 RAG

- “今天做了什么”“昨天有哪些邮件”等明确时间查询：直接按日期和游标查询，不使用向量检索。
- 当前邮件串、微信群或任务：优先读取当前 Thread 摘要和最近事件，不用全库相似搜索替代当前上下文。
- “上周中继协议改到哪里”“之前关于方案 B 怎么决定的”等模糊旧事项：使用结构化条件 + 关键词/向量混合 RAG，再按来源 ID 展开。
- 定时总结使用时间和游标，不依靠相似度搜索选择当天材料。

### 5.3 注入规则

- Router 默认只接收当前状态、相关摘要和少量来源 ID。
- Worker 接收当前目标、当前 Thread 摘要、最近事件和必要的检索补充。
- 原始全文按需展开，长文分段读取，不一次性注入全部历史。
- 邮件、微信和网页正文始终是不可信数据，不能借注入扩大工具权限。

## 6. 工作轨迹处理

工作轨迹量最大、噪音最高，不应把每条窗口事件都变成 Trigger，也不应全部向量化和注入。

### 6.1 保留现有采集

- 现有本地 JSONL、UIA/OCR、截图证据和工作轨迹浮窗继续保留。
- 原始轨迹和证据沿用现有保留策略。
- OCR/UIA 文本先脱敏，再允许索引；截图本身不向量化。
- 密码、Token、密钥等敏感内容不得进入模型或向量索引。

### 6.2 程序先切工作片段 Episode

根据时间间隔、应用切换、窗口标题、正文变化和用户主动标记，将连续轨迹组成工作片段。

只有片段完成、明显切换事项或用户主动标记时才产生 Trigger，不是每次窗口或鼠标事件都触发 Agent。

每个工作片段生成结构化摘要：

- 时间段和主要应用；
- 做了什么；
- 产出了什么文件、页面或结果；
- 完成、进行中还是受阻；
- 关键决定和问题；
- 原始证据 ID；
- 摘要覆盖到哪个轨迹游标。

### 6.3 每日工作总结

每日总结 Worker 按日期读取当天全部 Episode 摘要，不重新注入全部原始轨迹，也不通过 RAG 猜测当天内容。

工作片段摘要可以长期保存并建立索引；原始轨迹和截图按较短期限保留。

## 7. 邮件与微信总结

### 7.1 邮件

- 一封往来邮件串对应一个 Thread。
- 新邮件只触发该 Thread 的增量总结，不重新总结整个邮箱。
- 提取最新问题、决定、截止时间、附件和待办。
- 普通邮件只更新摘要；需要回复或执行时才创建 Action Worker。
- 回复草稿进入唯一主会话的审批卡，不自动发送。

### 7.2 微信

- 一个群或联系人对应一个 Thread。
- 默认保存和过滤，不是每条消息都调用模型。
- @用户、明确提问、关键词、关注人和已订阅任务才进入语义判断。
- 普通群聊按时间窗口形成低频摘要；每日总结只覆盖关注范围。
- 通知或可见内容不完整时，摘要必须标记“可能不完整”。

预留按账号、群、联系人配置允许/拒绝采集的策略，具体交互后续确定：

- 允许采集的内容才进入原始存储、摘要和索引。
- 禁止采集的正文在持久化前丢弃，不进入 RAG，不参与每日总结。
- 可以只保留跳过数量，不保留被禁止来源的正文。

## 8. 主会话中的每日简报

主会话每天优先展示一张“今日简报”卡，分为：

1. **需要你处理**：审批、明确问题、即将到期事项。
2. **重要变化**：决定、改期、任务完成和阻塞。
3. **后台已整理**：普通工作记录和低优先级消息摘要。

用户可在同一主会话继续追问：

- “今天主要做了什么？”
- “这个结论来自哪封邮件？”
- “群里对方案有什么意见？”
- “根据今天的情况安排明天工作。”

追问时由 Router 按来源 ID 展开 Thread 和证据，不跳转到其他聊天 Session。

## 9. Worker 经验提取

Worker 完成后不将全部原始对话和工具日志塞回主上下文，而应提取：

- 任务目标和完成结果；
- 关键结论与用户决定；
- 形成的稳定偏好或可复用经验；
- 遇到的问题及解决方式；
- 未决事项；
- 原始证据和 Worker 记录 ID。

提炼结果写入统一记忆和 Thread 摘要；原始 Worker 记录继续保留，默认只在需要审计或深入追问时展开。

## 10. 删除与一致性

- Trigger、Episode、摘要和索引都必须有稳定来源 ID。
- 同一来源重复采集不得重复生成摘要或任务。
- 同一 Thread 的摘要更新必须串行，摘要游标只能前进。
- 删除原始工作轨迹或消息时，同步删除对应向量索引，并删除或重新生成相关摘要，避免敏感内容残留。
- 摘要与原始事实冲突时，以原始证据为准，并允许重建摘要。

## 11. 实施优先级调整

最高优先级不是增加渠道或管理页面，而是完成：

```text
唯一主会话
→ 创建后台 Worker
→ Worker 完成
→ 结果与经验回到统一记忆
→ 主会话可继续追问和召回
```

随后依次完成：

1. 工作轨迹 Episode 与每日总结；
2. 邮件 Thread 与增量总结；
3. 微信可配置采集、低频总结和关注事项提取；
4. 跨渠道每日简报；
5. 辅助工作台和更多渠道能力。

## 12. 补丁验收标准

- 用户日常使用只需进入一个主会话，不需要选择 Router/Worker/Thread Session。
- 电脑和手机看到的是同一主会话及统一任务状态。
- “今天做了什么”通过日期和游标生成，不依赖向量相似度。
- 旧事项可以通过 RAG 找回，并按来源 ID 展开证据。
- 原始工作轨迹不会全量注入模型，也不会逐事件触发 Agent。
- 邮件和微信只对接收到的内容做增量总结，不重复总结整个渠道。
- 禁止采集的微信来源不会进入正文存储、索引或摘要。
- Worker 只将提炼后的结果和经验回到主会话，不直接形成第二个用户对话。
