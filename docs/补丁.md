# Super-agent 个人 Agent 架构改造计划书补丁

| 项目 | 内容 |
|---|---|
| 日期 | 2026-11-01 |
| 适用 | 《SuperAgent个人Agent架构改造计划书》v0.2 及后续版本 |
| 优先级 | 本补丁与原计划冲突时，以本补丁为准 |

## 1. 产品定位：单用户、单大脑、唯一主会话

本项目是单用户个人助手，不建设多用户、多租户或团队协作系统。

- 只有一个用户、一个身份、一个活跃大脑。
- 不提供用户切换、用户列表或跨用户管理。
- 数据库现有 `owner_user_id` 仅为兼容字段，可在内部绑定固定本地用户，不代表产品支持多用户。
- 客户端不再依赖手动传入 `X-User-Id` 选择身份；服务端在内部确定唯一本地用户。
- 安全重点是本机访问凭证、手机配对和设备权限，而不是多租户权限体系。
- 电脑和手机是同一个主会话的两个视图，不各自形成主聊天记录。

原计划中过重的 owner/token/scope 多用户设计，收缩为“单用户身份 + 配对设备鉴权 + 必要动作权限”。

## 2. DSH 核心吸收点：Session 下沉，主会话统一

底层允许多个 Session 并行，但用户始终只面对一个 Agent、一个主会话。

```text
                      唯一主会话
               电脑端和手机端共享同一视图
                           │
                           ▼
                  常驻 Router / 全局状态
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
      Worker A          Worker B          Worker C
      隐藏会话          隐藏会话          隐藏会话
          └────────────────┼────────────────┘
                           ▼
              结果、经验、未决事项回到统一记忆
```

- Router Session、Worker Session 都是实现细节，不让用户选择或管理。
- Thread 是后台上下文组织方式，不是新的用户聊天窗口。
- 邮件串、微信群、工作片段和项目讨论可以有独立 Thread，但不形成面向用户的独立助手。
- 任务、澄清和审批优先以卡片回到主会话；工作台只是辅助查看入口，不是另一个交互中心。
- 主会话在视觉上长期连续，但底层 Router 仍可压缩、重建和按需召回，不等于维护一个无限增长的 LLM 上下文。

## 3. 内部 Thread 与 Worker 的使用边界

不是每个应用永久运行一个 LLM Session，而是“事项持续保存为 Thread，需要时才运行 Worker”。

| 组件 | 使用方式 |
|---|---|
| Connector/Collector | 确定性采集、过滤、去重，不需要 LLM Session |
| Thread | 持续保存邮件串、微信群、工作片段等上下文 |
| Thread Summary Worker | 新事件累积后做增量总结；同一 Thread 串行更新 |
| Daily Digest Worker | 按日期和游标合并当天摘要，形成跨渠道简报 |
| Action Worker | 执行查资料、起草回复、处理任务等具体工作 |
| Router | 唯一面向用户的交互和全局协调入口 |

所有 Worker 都不直接对用户聊天，只把结果、证据和待决事项交给 Router。

## 4. 每日总结的统一链路

```text
工作轨迹 / 邮件 / 微信 / 日历
              │
              ▼
     确定性采集、过滤、去重、分段
              │
              ▼
       各自 Thread 原始记录
              │
       ┌──────┴────────┐
       ▼               ▼
Thread 总结 Worker   行动 Worker
增量总结、提取事项    查资料、写草稿、执行任务
       └──────┬────────┘
              ▼
       跨渠道每日总结 Worker
              │
              ▼
         常驻 Router
              │
              ▼
          唯一主会话
```

每日总结不是“工作总结 + 邮件总结 + 微信总结”的简单拼接，而应围绕同一事项合并：

- 今天发生了什么重要变化；
- 用户或相关人员做了什么决定；
- 哪些事项已完成、仍在推进或受到阻塞；
- 哪些事项需要用户处理；
- 下一步建议是什么；
- 每个结论对应的来源 Thread、事件和证据 ID。

晚到的事件可以产生简报新版本，但不能悄悄修改已经交付的简报；主会话应提示“简报有更新”。

## 5. 存储、RAG 与注入不是二选一

统一采用：

> 原始信息先存储，摘要作为派生数据，RAG 负责按需找回，最后只把当前任务需要的内容注入模型。

### 5.1 数据分层

| 层 | 保存内容 | 用途 |
|---|---|---|
| 原始层 | 邮件、微信、工作轨迹、时间和来源 ID | 证据、重放、重新总结 |
| Thread 层 | 最近事件、滚动摘要、摘要游标 | 保持事项连续性 |
| 索引层 | 脱敏正文和摘要的结构化/关键词/向量索引 | 按需检索 |
| 摘要层 | 工作片段摘要、每日简报、任务结果和经验 | 低成本默认上下文 |

原始记录是事实依据，摘要不能替代原始记录。摘要必须带来源 ID、覆盖时间和摘要游标。

### 5.2 什么时候使用 RAG

- “今天做了什么”“昨天有哪些邮件”等明确时间查询：直接按日期和游标查询，不使用向量检索。
- 当前邮件串、微信群或任务：优先读取当前 Thread 摘要和最近事件，不用全库相似搜索替代当前上下文。
- “上周中继协议改到哪里”“之前关于方案 B 怎么决定的”等模糊旧事项：使用结构化条件 + 关键词/向量混合 RAG，再按来源 ID 展开。
- 定时总结使用时间和游标，不依靠相似度搜索选择当天材料。

### 5.3 注入规则

- Router 默认只接收当前状态、相关摘要和少量来源 ID。
- Worker 接收当前目标、当前 Thread 摘要、最近事件和必要的检索补充。
- 原始全文按需展开，长文分段读取，不一次性注入全部历史。
- 邮件、微信和网页正文始终是不可信数据，不能借注入扩大工具权限。

## 6. 工作轨迹处理

工作轨迹量最大、噪音最高，不应把每条窗口事件都变成 Trigger，也不应全部向量化和注入。

### 6.1 保留现有采集

- 现有本地 JSONL、UIA/OCR、截图证据和工作轨迹浮窗继续保留。
- 原始轨迹和证据沿用现有保留策略。
- OCR/UIA 文本先脱敏，再允许索引；截图本身不向量化。
- 密码、Token、密钥等敏感内容不得进入模型或向量索引。

### 6.2 程序先切工作片段 Episode

根据时间间隔、应用切换、窗口标题、正文变化和用户主动标记，将连续轨迹组成工作片段。

只有片段完成、明显切换事项或用户主动标记时才产生 Trigger，不是每次窗口或鼠标事件都触发 Agent。

每个工作片段生成结构化摘要：

- 时间段和主要应用；
- 做了什么；
- 产出了什么文件、页面或结果；
- 完成、进行中还是受阻；
- 关键决定和问题；
- 原始证据 ID；
- 摘要覆盖到哪个轨迹游标。

### 6.3 每日工作总结

每日总结 Worker 按日期读取当天全部 Episode 摘要，不重新注入全部原始轨迹，也不通过 RAG 猜测当天内容。

工作片段摘要可以长期保存并建立索引；原始轨迹和截图按较短期限保留。

## 7. 邮件与微信总结

### 7.1 邮件

- 一封往来邮件串对应一个 Thread。
- 新邮件只触发该 Thread 的增量总结，不重新总结整个邮箱。
- 提取最新问题、决定、截止时间、附件和待办。
- 普通邮件只更新摘要；需要回复或执行时才创建 Action Worker。
- 回复草稿进入唯一主会话的审批卡，不自动发送。

### 7.2 微信

- 一个群或联系人对应一个 Thread。
- 默认保存和过滤，不是每条消息都调用模型。
- @用户、明确提问、关键词、关注人和已订阅任务才进入语义判断。
- 普通群聊按时间窗口形成低频摘要；每日总结只覆盖关注范围。
- 通知或可见内容不完整时，摘要必须标记“可能不完整”。

预留按账号、群、联系人配置允许/拒绝采集的策略，具体交互后续确定：

- 允许采集的内容才进入原始存储、摘要和索引。
- 禁止采集的正文在持久化前丢弃，不进入 RAG，不参与每日总结。
- 可以只保留跳过数量，不保留被禁止来源的正文。

## 8. 主会话中的每日简报

主会话每天优先展示一张“今日简报”卡，分为：

1. **需要你处理**：审批、明确问题、即将到期事项。
2. **重要变化**：决定、改期、任务完成和阻塞。
3. **后台已整理**：普通工作记录和低优先级消息摘要。

用户可在同一主会话继续追问：

- “今天主要做了什么？”
- “这个结论来自哪封邮件？”
- “群里对方案有什么意见？”
- “根据今天的情况安排明天工作。”

追问时由 Router 按来源 ID 展开 Thread 和证据，不跳转到其他聊天 Session。

## 9. Worker 经验提取

Worker 完成后不将全部原始对话和工具日志塞回主上下文，而应提取：

- 任务目标和完成结果；
- 关键结论与用户决定；
- 形成的稳定偏好或可复用经验；
- 遇到的问题及解决方式；
- 未决事项；
- 原始证据和 Worker 记录 ID。

提炼结果写入统一记忆和 Thread 摘要；原始 Worker 记录继续保留，默认只在需要审计或深入追问时展开。

## 10. 删除与一致性

- Trigger、Episode、摘要和索引都必须有稳定来源 ID。
- 同一来源重复采集不得重复生成摘要或任务。
- 同一 Thread 的摘要更新必须串行，摘要游标只能前进。
- 删除原始工作轨迹或消息时，同步删除对应向量索引，并删除或重新生成相关摘要，避免敏感内容残留。
- 摘要与原始事实冲突时，以原始证据为准，并允许重建摘要。

## 11. 实施优先级调整

最高优先级不是增加渠道或管理页面，而是完成：

```text
唯一主会话
→ 创建后台 Worker
→ Worker 完成
→ 结果与经验回到统一记忆
→ 主会话可继续追问和召回
```

随后依次完成：

1. 工作轨迹 Episode 与每日总结；
2. 邮件 Thread 与增量总结；
3. 微信可配置采集、低频总结和关注事项提取；
4. 跨渠道每日简报；
5. 辅助工作台和更多渠道能力。

## 12. 补丁验收标准

- 用户日常使用只需进入一个主会话，不需要选择 Router/Worker/Thread Session。
- 电脑和手机看到的是同一主会话及统一任务状态。
- “今天做了什么”通过日期和游标生成，不依赖向量相似度。
- 旧事项可以通过 RAG 找回，并按来源 ID 展开证据。
- 原始工作轨迹不会全量注入模型，也不会逐事件触发 Agent。
- 邮件和微信只对接收到的内容做增量总结，不重复总结整个渠道。
- 禁止采集的微信来源不会进入正文存储、索引或摘要。
- Worker 只将提炼后的结果和经验回到主会话，不直接形成第二个用户对话。

## 13. 免费渠道接入方案（本期）

### 13.1 范围与免费边界

本期只使用现有账号已经具备的免费能力、官方免费额度和本地开源组件，不购买第三方消息中台、邮件中台、公网回调服务或企业微信会话内容存档。

| 渠道 | 本期方式 | 能力承诺 | 费用与前提 |
|---|---|---|---|
| 邮箱 | 现有 IMAP 只读轮询 | 不打开邮箱客户端，按账号、文件夹、发件人、主题和日期采集；支持已有邮件和增量邮件 | 使用现有邮箱的免费 IMAP；无第三方邮件服务 |
| 飞书 | 官方 Go SDK + 历史消息 API + WebSocket | 机器人所在的授权单聊/群可按 `chat_id` 补拉历史并接收新消息 | 使用免费版开放能力和额度；需要应用权限及机器人入群 |
| 钉钉 | 官方 Go Stream SDK | 接收机器人实际可收到的新消息，保存群 ID、群名、发送者、时间和正文 | 使用免费机器人/Stream 额度；不承诺完整历史 |
| 电脑微信 | 现有本地 UIA/OCR | 用户授权后读取当前聊天可见内容 | 本地免费；不读取数据库、不 Hook、不注入 |
| 手机微信 | Android 通知监听 | 用户授权后保存通知中实际出现的标题和正文 | 本地免费；通知关闭或聚合时可能不完整 |
| 企业微信 | 本期不接 | 不以普通机器人接口冒充会话存档 | 会话内容存档收费，明确排除 |

飞书历史消息与钉钉 Stream 均直接连接官方服务，不依赖付费中继。钉钉只保存接入后机器人实际收到的消息，不通过界面自动化补抓全量历史。

### 13.2 每项能力独立开关

`activity`、`email`、`feishu`、`dingtalk`、`wechat_desktop`、`wechat_mobile` 分别保存以下策略，默认全部关闭：

```text
enabled               是否采集新信息
summary_enabled       是否调用模型生成 Thread 摘要
index_enabled         是否生成向量索引并进入长期记忆召回
brief_enabled         是否纳入每日简报
auto_worker_enabled   是否允许 Router 因该渠道事件自动创建 Worker
```

全局另设 `router_enabled`、`worker_enabled`、`daily_brief_enabled` 和 `proactive_notify_enabled`，不与渠道采集开关捆绑。渠道的自动 Worker 只有在本渠道和全局都允许时才可创建。

开关语义必须一致：

- 关闭 `enabled`：在采集端停止，不把新正文发送到服务端；旧数据不自动删除。
- 关闭 `summary_enabled`：原始记录可按授权保存，但不因新事件调用总结模型。
- 关闭 `index_enabled`：不生成新向量，不影响按日期、来源 ID 和关键词查询。
- 关闭 `brief_enabled`：该渠道不进入自动或手动每日简报。
- 关闭 `auto_worker_enabled`：仍可采集、总结和生成简报，但不自动执行任务。
- 关闭每日简报：不自动生成，保留其他渠道和手动总结能力。

飞书、钉钉和微信的新群/联系人默认拒绝，必须显式加入允许列表。邮箱以显式启用的账号和文件夹为授权范围。任何被拒绝的正文都必须在持久化、向量化、摘要和旧通知中心入库之前丢弃，只保留跳过计数。

### 13.3 统一接入链路

```text
免费 Connector
→ 本渠道 enabled 检查
→ 群/联系人/账号 allow/deny 检查
→ 外部消息 ID 去重
→ 原始 Trigger + 对应 Thread
→ 按开关生成摘要 / 索引 / 简报 / Worker
→ 结果只回唯一主会话
```

所有 Connector 使用现有 `agent_channel_policy`、`agent_channel_cursor` 和 EventLog，不另建平行消息队列。群名、联系人名只用于展示和选择，内部以不可变的账号、`chat_id`、`conversationId` 等 ID 关联，避免改名或重名造成串话。

### 13.4 各渠道实施约束

**邮箱**

- 复用 `internal/email`，不引入网页邮箱自动化。
- 补齐 `UIDVALIDITY + UID`，防止邮箱重置后漏信或串信；增加服务端发件人、主题、日期和文件夹筛选。
- 保持 `BODY.PEEK[]` 只读，不修改已读状态，不在本期自动发送。
- 密码不进入日志、模型或中继；真实邮箱验收前不宣称生产可用。

**飞书**

- 使用官方 `larksuite/oapi-sdk-go`，不使用第三方付费消息中台。
- 先列出机器人可见群/单聊，由用户按名称选择并保存对应 `chat_id`。
- 首次按页补拉所选会话的限定范围，之后 WebSocket 收新消息；定时 REST 补拉处理断线缺口。
- 以 `message_id` 幂等去重，一个 `chat_id` 对应一个 Thread；历史补拉和实时消息共用同一游标与去重链路。
- 无权限、未入群或额度受限时显示真实状态，不降级为界面抓取。

**钉钉**

- 使用官方 `open-dingtalk/dingtalk-stream-sdk-go`，不增加公网 HTTP 回调依赖。
- 保存 `conversationId`、`conversationTitle`、`msgId`、发送者、时间和正文，以 `msgId` 去重。
- 只处理机器人实际收到的消息；未 @ 机器人而收不到的消息不得伪装为已采集。
- 不做个人钉钉数据库读取、Hook 或全量历史界面翻页。

**个人微信**

- 电脑默认只提供“读取当前聊天”，不自动遍历群列表、不自动翻全部历史、不操作发送控件。
- “指定聊天读取”后续只能作为单独开关的增强能力：用户明确选择群/联系人和读取范围后，才可进行有限 UIA 导航；失败即停止。
- 手机微信通知在进入旧 `/api/inbox/events` 前应用同一微信开关和来源策略，不能绕过新渠道隐私边界。
- 可见快照和通知都标记“可能不完整”，不伪造逐条完整消息或发送人。

### 13.5 执行顺序

1. **统一开关与隐私前置**：实现六类渠道策略、四个全局开关和工作台设置；修复 Android 微信通知绕过策略的问题。
2. **邮箱真实闭环**：在现有 IMAP 上补游标和筛选，使用免费测试邮箱验证后台拉取、独立开关、摘要和简报。
3. **通用网页采集与归纳**：实现 Browser Collector、通用正文提取、变化检测、站点开关和增量总结，以 QQ 邮箱和 BOSS 直聘作为验收样例。
4. **浏览器会话与自动登录**：先实现 SecretStore，再按站点开放会话恢复、凭据填充和人工验证接续；随后按需增加站点适配器。
5. **飞书完整闭环**：完成授权会话选择、限定历史补拉、WebSocket 新消息、断线补拉和统一 Thread。
6. **钉钉新消息闭环**：完成 Stream 接入、机器人可见消息保存、去重和简报，不扩展为历史抓取。
7. **个人微信安全增强**：完善当前聊天读取、来源识别和手机通知统一过滤；指定聊天自动导航另行验收，不阻塞其他渠道。

### 13.6 免费渠道验收标准

- 所有渠道默认关闭；只开启一个渠道时，其他渠道没有网络采集、正文入库或模型调用。
- 企业微信会话存档不出现在本期依赖、设置或实现中，没有付费第三方消息/邮件中台。
- 邮箱客户端未打开时仍能按授权范围拉取邮件，且不改变已读状态。
- 飞书只读取用户选择的群/联系人；历史补拉与实时消息重复时不产生重复 Trigger 或摘要。
- 钉钉断线重连后可继续接收，但不展示未实际取得的历史消息。
- 被拒绝的微信、飞书、钉钉来源在旧通知中心、Trigger、向量索引、摘要和简报中均无正文残留。
- 关闭摘要、索引或简报后，对应模型/向量化/生成任务确实不再执行，不只是隐藏界面。
- 电脑微信默认没有自动点击、滚动和发送行为；手机微信可独立关闭而不影响其他通知。
- 免费额度、权限不足和机器人未入群均有可见错误，不通过付费服务或非官方协议悄悄绕过。

## 14. 通用网页采集、归纳与自动登录

### 14.1 定位：完整 Web 信息能力，不是两个站点插件

QQ 邮箱和 BOSS 直聘只是验收样例。本期建设的是通用 Browser Collector：用户给出授权网站、账号和页面范围后，系统能够读取当前网页或按计划在后台采集，发现新增与变化内容，形成页面/站点摘要并纳入统一记忆和每日简报。

工作轨迹回答“用户当时在做什么”，Browser Collector 回答“授权网站出现了哪些信息、发生了什么变化”。它不依赖用户一直打开页面，也不让 BMA 定时模拟人反复点击。

“通用”指不要求每个网站都开发适配器，但不承诺所有网站都能完整解析。无法可靠提取时必须显示 `generic`、`adapter` 或 `ocr_fallback` 等采集方式和完整性，不能把 OCR 片段伪装成完整网页。

### 14.2 完整处理链路

```text
授权 URL / 当前页面 / 定时任务
→ 浏览器会话与自动登录
→ 域名、路径、页数和时间范围检查
→ 站点适配器或通用正文提取
→ 条目规范化、内容 hash、变化检测
→ 原始网页条目 + 来源 URL + 证据
→ 页面/事项 Thread 增量归纳
→ 按开关建立索引、生成简报或创建 Worker
→ 结果只回唯一主会话
```

Browser Runtime 使用免费开源 Playwright 和独立浏览器配置文件，不购买浏览器云、代理、打码或付费采集服务。后台采集不接管日常浏览器，不读取其他标签页。

### 14.3 通用提取与站点适配

按以下顺序提取，不要求新网站必须写代码：

1. **站点适配器**：针对高频或高价值网站提取稳定条目 ID、列表、详情、作者和时间，使用本地页面样本测试。
2. **通用正文提取**：读取 DOM、可访问性树、页面元数据和语义结构，去除导航、广告、脚本及重复页脚，识别标题、正文、链接和列表。
3. **可见内容兜底**：现有 UIA/OCR 只用于当前页面或 DOM 无法读取的区域，并明确标记可能不完整。

通用页面按规范化 URL、页面提供的条目 ID 和内容 hash 去重；没有稳定条目 ID 时使用“站点 + 规范化 URL + 内容 hash”，不能仅凭标题猜测同一事项。列表页用于发现新增和变化，只有需要归纳或发生变化时才读取详情。

后台导航必须限制在用户提供或明确授权的起始 URL、域名和路径内，并设置采集间隔、最大页数、最大深度和单轮时长。分页和滚动只读取授权范围，遇到登录失效、验证码、访问限制或网站拒绝时停止，不尝试绕过。

### 14.4 网页归纳与记忆

网页信息不是每次刷新都全量总结，而是分为：

- **当前页归纳**：用户询问时总结当前页面主要结论、事项、链接和待办。
- **单页增量归纳**：内容变化时只总结新增、删除和修改部分，保留前后版本与来源 URL。
- **列表/网站动态**：把多个新条目按事项归并，输出“新增、重要变化、待处理、低优先级动态”。
- **跨网页每日简报**：按日期和游标读取当天网页条目摘要，不重新注入全部网页正文。

原始网页条目至少保存站点、账号别名、条目 ID、规范化 URL、标题、正文、页面显示时间、采集时间、内容 hash 和采集方式。随后沿用“原始记录 → Thread 摘要 → 按需索引 → 简报”链路；追问时按 URL 和来源 ID 展开证据。

### 14.5 自动登录与会话恢复

自动登录是独立能力，由 Browser Session Manager 负责，不让 BMA 或模型接触明文密码。每个站点单独配置 `session_enabled`、`auto_login_enabled` 和 `credential_ref`，默认全部关闭。

登录按以下顺序执行：

1. **恢复已有会话**：优先复用该站点独立浏览器配置文件中的有效登录状态，不导出 Cookie 或会话令牌。
2. **用户手动登录**：首次接入、扫码、二次验证或表单无法确认时，由用户在浏览器中完成，采集器随后只检测登录结果。
3. **授权凭据填充**：用户明确开启后，SecretStore 将账号密码直接交给浏览器填充逻辑，不经过 Router、Worker、BMA、Trigger、日志或模型上下文。

凭据填充必须满足：

- 先完成 Windows DPAPI SecretStore；不把网页密码保存在明文 settings、数据库正文或日志中。
- 只允许在用户预先确认的准确 HTTPS 域名和登录路径填充；跳转域名变化、证书异常或表单来源不明时停止。
- 首次登录表单及表单结构变化后需用户确认；优先使用确定性站点适配器，不让模型猜测密码框并输入。
- 验证码、扫码、短信/动态口令和二次验证由用户接续，不绕过、不购买打码服务；连续失败立即停止，避免账号锁定。
- 自动登录成功只恢复该站点的读取权限，不代表获得发送、发布、投递、删除、支付或修改账号资料的权限。

### 14.6 独立权限与 BMA 分工

每个网站/账号分别具有：

```text
enabled               采集新信息
summary_enabled       页面和事项归纳
index_enabled         向量索引与长期记忆召回
brief_enabled         纳入每日简报
auto_worker_enabled   因网页变化自动创建 Worker
navigation_enabled    在授权 URL 范围内自动分页/滚动
auto_login_enabled    使用授权凭据自动登录
```

默认全部关闭。`navigation_enabled` 和 `auto_login_enabled` 不赋予任何外部动作权限；发送、发布、投递、删除、支付等仍必须经过 ActionOutbox 人工审批。

| 组件 | 负责 | 不负责 |
|---|---|---|
| Browser Collector | 会话恢复、授权导航、通用/适配器提取、变化检测和增量 Trigger | 不自动执行外部动作，不绕过验证 |
| 工作轨迹 | 保留用户实际操作、UIA/OCR 和必要证据 | 不承担定时结构化网页同步 |
| BMA 电脑操控 | 用户明确发起的一次性特殊操作和经审批的外部动作 | 不做常驻采集器，不保存或传递明文网页密码 |

### 14.7 样例网站的适配规则

- **QQ 邮箱网页版**：仍优先 IMAP；网页结果按 Message-ID 或账号、主题、收发件人和时间与 IMAP 去重，不修改已读状态、不自动发送。
- **BOSS 直聘网页版**：按页面实际提供的职位/会话 ID 归 Thread；不自动投递、聊天或交换联系方式。
- **其他网站**：无需等待专门插件，可先使用通用提取和归纳；只有通用结果不足或需要稳定字段、自动登录表单时再增加适配器。

### 14.8 通用网页能力验收标准

- 一个未专门适配的授权网页也能完成正文提取、摘要和来源回溯，并明确显示提取方式与完整性。
- 同一页面未变化时不重复总结；变化时只处理差异，列表刷新不产生重复事项。
- 后台导航不会离开授权域名和路径，不会超过页数、深度或时间限制。
- 自动登录关闭时只尝试已有会话或提示人工登录，不读取 SecretStore 凭据。
- 密码从 SecretStore 直接到浏览器填充逻辑，模型、BMA、日志、Trigger 和调试截图均不可见。
- 非预期域名、验证码、二次验证和连续登录失败均停止并请求用户处理，不自动绕过。
- 登录成功后仍只有采集权限；任何发送、发布、投递、删除或支付都必须另行审批。
- 站点关闭时不启动浏览器、不读取页面、不产生采集或模型调用，也不影响其他网站和 BMA 人工任务。

## 15. 通用网页能力开源选型与开工设计

### 15.1 已评估项目与采用结论

| 项目 | 已核实能力 | 本期结论 |
|---|---|---|
| [Playwright](https://github.com/microsoft/playwright) | 本地浏览器自动化、持久会话、DOM/可访问性树、表单填充、截图，支持 Chromium/Edge | **采用 `playwright-core` 作为 Browser Runtime** |
| [Mozilla Readability](https://github.com/mozilla/readability) | Firefox Reader View 同源正文提取，输出标题、正文、作者、时间和站点信息 | **采用 `@mozilla/readability` 作为通用文章提取器** |
| [changedetection.io](https://github.com/dgtlmoon/changedetection.io) | 定时监控、CSS/XPath 过滤、变化通知、Playwright Browser Steps 登录和 AI 摘要 | 能力可用，但会引入第二套调度、配置和凭据体系；不作为核心依赖 |
| [Crawl4AI](https://github.com/unclecode/crawl4ai) | 网页转 Markdown、结构化提取、深层抓取、持久浏览器配置和本地服务 | 能力可用，但需 Python/Docker sidecar；首版不为重复能力增加运行时 |
| [Stagehand](https://github.com/browserbase/stagehand) | 本地浏览器、`observe/act/extract`、持久会话；可只把选择器交给模型而不发送密码 | 作为后续自愈导航/表单辅助选项，首版不强制增加模型调用 |
| [browser-use](https://github.com/browser-use/browser-use) | 本地 AI 浏览器 Agent、真实浏览器配置文件和任务回放 | 与 BMA 的通用电脑操控重叠，不作为确定性采集基座 |

结论：没有一个项目应原样替代本产品。首版采用 **Playwright + Readability + 现有 Super-agent**，自研部分只保留 URL 权限、增量归一化、统一开关、现有 Thread 映射和 SecretStore 衔接，不重新实现浏览器、正文阅读器或第二套网页监控平台。

### 15.2 首版依赖与复用点

新增桌面依赖仅：

```text
playwright-core        使用本机已安装的 Edge/Chrome，不下载额外 Chromium
@mozilla/readability   通用文章正文提取
```

优先使用 `channel: "msedge"`，不可用时回退本机 Chrome；不安装 stealth、打码、代理或云平台组件。Playwright 持久配置文件按“站点 + 账号别名”隔离，首次使用可见浏览器窗口，只有具体站点验证后才允许该站点后台/无头运行。

继续复用：

- `desktop/redaction.js`：正文入库前脱敏；
- `desktop/assistant-api.js`：网页条目上报；
- `agent_channel_policy`：站点/账号 allow/deny；
- `agent_channel_cursor`：站点采集游标；
- `SuperAgent.Ingest`：Trigger、Thread、EventLog 和幂等；
- 现有 Thread Summarizer、统一记忆和 DailyBrief；
- 现有 BMA：只处理一次性特殊操作，不进入常驻采集链。

### 15.4 站点配置契约

`settings.json` 增加 `web.sites`，所有开关默认 false：

```json
{
  "web": {
    "sites": [
      {
        "id": "site-id",
        "account": "账号别名",
        "enabled": false,
        "start_urls": ["https://example.com/authorized/path"],
        "allowed_origins": ["https://example.com"],
        "allowed_path_prefixes": ["/authorized/"],
        "interval_seconds": 1800,
        "max_pages": 5,
        "max_depth": 1,
        "summary_enabled": false,
        "index_enabled": false,
        "brief_enabled": false,
        "auto_worker_enabled": false,
        "navigation_enabled": false,
        "session_enabled": false,
        "auto_login_enabled": false,
        "credential_ref": ""
      }
    ]
  }
}
```

采集间隔低于 60 秒、页数/深度超过上限时由设置 API 拒绝。凭据只通过 `credential_ref` 关联 SecretStore；站点配置、HTTP 响应和日志均不得出现密码、Cookie 或令牌。

### 15.5 网页条目与去重契约

桌面上报：

```json
{
  "site_id": "site-id",
  "account": "账号别名",
  "url": "https://example.com/item/42",
  "canonical_url": "https://example.com/item/42",
  "item_id": "42",
  "title": "条目标题",
  "text": "脱敏后的正文",
  "captured_at": "RFC3339",
  "extracted_by": "adapter|readability|dom|ocr_fallback",
  "completeness": "complete|partial|unknown",
  "evidence_ids": []
}
```

服务端校验站点开关、来源策略、URL 和正文大小，并对规范化正文重新计算 SHA-256。首版不新建网页业务表：

```text
Channel           web
Kind              web_item
ExternalID        web:<site>:<account>:<item>:<content_hash>
ThreadExternalID  web:<site>:<account>:<canonical_url>
Payload           URL、提取方式、完整性、采集时间、证据 ID
```

同一内容重复刷新返回原 Trigger；内容变化形成同一 Thread 的新版本。`internal/superagent/summary.go` 的自动摘要渠道和 `internal/superagent/brief.go` 的日期汇总渠道必须加入 `web`，同时受站点摘要/简报开关约束。

### 15.6 API 与桌面 IPC

首版 API：

```text
POST /api/channels/web/items
GET  /api/settings/web/sites
PUT  /api/settings/web/sites/{id}
```

桌面 IPC：

```text
browser:read-current    读取当前授权页面，不点击、不翻页
browser:run-site        立即执行一次站点采集
browser:login-site      打开独立 profile 并接续人工登录
browser:stop            停止当前站点采集并关闭对应浏览器上下文
```

工作台提供站点增删、URL 范围、各项开关、立即采集、登录接续和最近错误。Router 不直接获得浏览器任意点击工具；外部动作继续走 ActionOutbox。

### 15.7 可直接执行的提交顺序

1. **开源组件冒烟**：安装两个 npm 依赖，用临时 profile 启动本机 Edge，验证本地 HTML 样例的 DOM/Readability 提取；确认打包环境无需下载浏览器。
2. **权限与入库**：实现站点配置、URL 策略、`POST /api/channels/web/items`、服务端 hash 和 Thread 幂等；先不启动定时器。
3. **当前页读取**：接通 Browser Runtime、通用提取、脱敏、桌面 IPC 和主会话结果；未知网站可手动触发并看到提取方式。
4. **定时增量**：实现站点调度、single-flight、页数/深度限制、变化检测、立即采集和错误状态；把 `web` 接入摘要与简报开关。
5. **会话恢复**：实现独立 profile、人工登录接续和会话失效提示；先验收登录状态可恢复，不启用密码填充。
6. **自动登录**：先实现 DPAPI SecretStore，再实现准确 origin 校验、用户确认的表单映射、SecretStore 到 Playwright 的直接填充和失败停止。
7. **样例适配与发布**：用 QQ 邮箱、BOSS 直聘验证去重和外部动作边界；补打包白名单、桌面 smoke 和真实网站人工验收。

每一步都可独立提交；第 1–4 步形成无密码的通用采集闭环，第 5–6 步才开放登录能力，不能在 SecretStore 未完成时把密码写入 settings 或交给 BMA。

### 15.8 开工验收命令与真实场景

每个阶段运行：

```text
npm --prefix desktop test
npm --prefix desktop run check
go test ./...
go vet ./...
```

涉及打包时运行 `npm --prefix desktop run dist` 和打包版 `--smoke-test`。真实验收至少覆盖：

- 未适配公开网页的正文提取、摘要、来源 URL 和重复刷新；
- 授权列表的新增/修改条目与最大页数限制；
- 关闭某站点后无浏览器启动、网络采集、摘要或索引；
- 手动登录后重启 profile 会话恢复；
- 自动登录时密码不出现在模型请求、日志、Trigger、截图和设置 API；
- 验证码/二次验证回到主会话等待人工，不发生自动绕过或连续登录；
- QQ 邮箱与 IMAP 去重，BOSS 不发生自动投递或聊天；
- 页面含“忽略之前指令”等文字时只能作为网页数据，不能扩大工具权限。
