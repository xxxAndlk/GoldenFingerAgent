# 感知采集层重设计方案：微信、网页与工作轨迹

> 日期：2026-11-03  
> 依据：当前 Go、Electron 源码与新 Super-agent／WorkTask 架构。  
> 目标：让系统真正知道“发生了什么”，并能解释采集是否完整、是否成功入库、为何被过滤；不以功能名称代替真实能力。
>
> 实施状态（2026-11-03）：M0–M4 已落地；独立微信连接器、持久 Spool、网页检查点、Episode 上下文分段和工作台健康状态已接线；微信真实会话已完成入库与重启幂等验收。详细证据见 `.agent/progress.md`。
>
> **微信部分已被替换**：`docs/微信本地数据库连接器完整迁移方案.md` 将“当前窗口截图 + OCR”替换为只读本地数据库连接器；本文件第 6 节和 M1 的可见窗口方案仅保留为历史，不再作为实施依据。

## 1. 结论

需要重新设计的是**感知采集层、可靠投递和采集可观测性**，不需要推翻现有 Trigger、Thread、Router、WorkTask、Worker 与记忆架构，也不需要重写全部采集器。

三类功能当前不在同一完成度：

| 功能 | 当前真实状态 | 判断 |
|---|---|---|
| 电脑微信消息 | 只有前台微信可见文本转发试验和服务端接收入口 | **尚未实现到可用程度，需要独立重做连接器** |
| 网页监听 | Playwright 采集、授权范围、正文提取、内容 hash、Trigger／Thread 主链路已存在 | **保留采集器，补持久调度、检查点和故障恢复** |
| 工作轨迹 | UIA／OCR、正文去重、本地 JSONL、截图证据、阶段总结已存在 | **保留观察与总结，重做 Episode 分段和任务关联** |

最重要的产品修正是：

> “已配置接收入口”不等于“已经看见消息”；“窗口曾被观察到”不等于“消息已完整入库”；“生成过总结”不等于“已关联到正确的长期任务”。

## 2. 当前源码暴露的实际问题

### 2.1 微信：不是独立消息监听器

`desktop/main.js` 的 `forwardWeChatActivity` 挂载在通用 `ActivityTrail.onEvent` 上，只是在工作轨迹事件中筛选微信窗口。因此它受工作轨迹是否观察、前台窗口、轮询时机和正文识别结果共同限制。

当前行为存在以下边界：

1. 只能看到当前前台微信窗口的可见区域，后台聊天、未打开会话和已滚出区域没有可靠采集闭环。
2. 整段可见正文被当成一条 `visible_content`，没有聊天气泡边界；`sender` 固定为空，无法可靠区分发送者和消息方向。
3. `source` 来自窗口标题，授权又按标题精确匹配；标题不等于稳定的会话身份。
4. 只用内存中的单个 `lastWeChatFingerprint` 去重，重启即丢失，也可能把同一会话里连续两次相同文本误判为重复。
5. 上报失败被空 `catch` 吞掉，没有本地待发队列、重试、健康状态或用户可见错误。
6. 渠道默认关闭、来源默认拒绝是必要的安全设计，但当前界面没有把“未启用、未授权、没观察到、观察后过滤、上传失败”清楚地区分出来。

服务端 `POST /api/channels/wechat/messages` 已能创建 Trigger／Thread，并给可见采集追加“可能不完整”，但这只证明**接收端存在**，不证明桌面端能看见消息。

### 2.2 网页：主链路已存在，后台可靠性不足

`desktop/browser-collector.js` 已具备真实页面采集、单站点 single-flight、导航深度与页面数限制、授权 origin／路径校验、登录停止、正文提取和结果上报，不应重写。

需要补的是：

- `running`、`status`、`lastRunAt` 都只在内存，重启后调度状态丢失。
- `seen` 只在单轮有效，跨轮主要依靠内容 hash 去重，没有页面级采集检查点。
- 调度器随浏览器采集器按需初始化；没有打开相关界面时，不能把它视为始终在后台运行。
- 调度、登录、提取、上传失败主要进入日志或内存状态，缺少统一、持久、可查询的健康记录。
- 内容 hash 能识别版本，却还缺“新增、更新、无变化、无法判断”的统一变更语义。

### 2.3 工作轨迹：记录存在，任务语义不够准确

现有本地持久化、300 条界面展示、5000 条恢复、截图证据保留和内容去重都应保留。协作模式只把完成的阶段总结送入事件层，而不是把所有原始截图与轨迹塞给模型，这个边界是正确的。

缺口在于：

- Episode 只带首个观察事件的应用名，跨应用工作片段的上下文表达不足。
- Episode 上报失败只记录日志，没有进入可靠重试队列。
- `activity:<日期>` 把一天内不同项目放进同一个 Thread，不利于关联长期 WorkTask。
- `evidence_ids` 目前只是本地事件 ID 列表，尚缺统一的证据定位、权限和保留期语义。
- 分段主要以时间为边界，没有充分利用项目、文档、页面和空闲间隔等上下文变化。

## 3. 目标架构

```text
电脑微信连接器      网页连接器       工作轨迹分段器
      │                  │                  │
      └────────── 统一 Observation Envelope ──────────┘
                           │
                隐私与来源授权前置过滤
                           │
              本地持久 Spool＋连接器检查点
                           │
                 服务端幂等接收／健康上报
                           │
                    Trigger／Thread
                           │
             Router／WorkTask Inbox／Summary
                           │
                 Memory／Brief／用户通知
```

### 职责边界

- **连接器**负责观察和如实描述完整性，不做长期任务判断。
- **Spool**负责至少一次投递、重启恢复和可见错误，不把“已写入本地”冒充“已入库”。
- **Trigger／Thread**继续作为服务端标准事件入口和上下文容器。
- **Router**只在采集可靠后决定通知、关联任务或创建任务；低置信度仍进入询问或建议，不强行改写任务。
- **Memory**保存有长期价值的事实和情景，不把所有页面正文、微信快照与鼠标活动永久记忆化。

## 4. 统一 Observation Envelope

三类采集共用信封，不强迫正文结构完全一致：

```json
{
  "schema_version": 1,
  "event_id": "桌面端生成的稳定 UUID",
  "channel": "wechat_desktop | web | activity",
  "kind": "message | visible_snapshot | page_version | work_episode",
  "source": {
    "connector_id": "wechat-uia",
    "source_id": "会话／站点／工作上下文的稳定标识",
    "display_name": "用户可识别的名称",
    "account": "可选，不知道则为空"
  },
  "occurred_at": null,
  "observed_at": "必须存在的实际观察时间",
  "completeness": "complete | current_visible | partial | unknown",
  "title": "标题",
  "text": "经授权和脱敏后的正文或摘要",
  "content_hash": "正文哈希，不单独充当消息身份",
  "change": {
    "type": "new | updated | unchanged | unknown",
    "previous_hash": "可选"
  },
  "evidence": [
    {
      "ref": "本地证据引用，不是默认发给模型的正文",
      "kind": "screenshot | activity_event | page_snapshot",
      "redacted": true,
      "expires_at": "可选"
    }
  ],
  "privacy": {
    "policy_version": "授权策略版本",
    "redacted": true
  },
  "cursor": "连接器自己的增量检查点"
}
```

关键语义：

- 不知道消息真实发送时间时，`occurred_at=null`，不能用观察时间伪装发送时间。
- 不知道发送者、会话或方向时明确为 `unknown`，不得猜测。
- `event_id` 用于投递幂等；`content_hash` 用于内容变更判断，两者不能混用。
- `current_visible` 永久保留“只见当前可见区域”的含义，不能在后续摘要中升级为完整历史。

## 5. 可靠投递与采集健康

### 5.1 本地持久 Spool

所有允许采集的 Observation 按以下顺序处理：

1. 在桌面端先执行渠道开关、来源授权和敏感内容过滤。
2. 允许采集的内容先追加到本地持久 Spool，再尝试上传。
3. 服务端确认接收或返回已存在的幂等结果后，才标记 delivered。
4. 服务停止、网络异常或进程重启后，从未确认记录恢复并有限重试。
5. 服务端拒绝来源或策略被撤销时，删除待发正文，只保留不含正文的过滤计数与原因。
6. 外部动作超时不能自动重试；这里的长效重试只适用于幂等的观察事件入库。

可使用追加式 JSONL＋确认标记实现首版，不必为了 Spool 引入外部消息队列。后续规模不足时再接 NATS、Redis Streams 等，语义不变。

### 5.2 每个连接器统一显示的健康状态

工作台与桌面设置至少展示：

- 当前状态：关闭、等待授权、观察中、降级、错误。
- 最近观察时间：采集器确实看到了什么。
- 最近新事件时间：最近一次识别到有效变化。
- 最近入库时间：服务端最近一次确认接收。
- 待发数量、最后错误、过滤原因与跳过计数。
- 当前完整性：完整、当前可见、部分或未知。
- “测试采集”按钮：只测试用户明确授权的会话／站点，显示脱敏后的结果和各阶段状态。

这样可以直接回答“为什么看不见”，而不是只显示一个已开启开关。

## 6. 电脑微信连接器重设计

### 6.1 第一版能力承诺

第一版只承诺：

> 在用户明确授权后，增量记录**当前打开会话中能够识别的可见消息**；无法识别时保存为可见快照并标记不完整。

不承诺个人微信后台全量消息、所有群历史或未打开会话的完整同步。继续坚持不读取微信数据库、不 hook、不注入、不使用非官方协议，不自动遍历群列表、翻历史或发送消息。

手机通知镜像或 Windows 可见通知可作为补充来源，但只能标记为“通知可见片段”，不能冒充完整聊天记录。

### 6.2 独立采集生命周期

新增 `WeChatConnector`，不再依附 `ActivityTrail.onEvent`：

- 微信渠道与工作轨迹窗口可以独立开关。
- 微信连接器只在渠道启用且存在授权会话时启动。
- UIA 优先识别聊天列表、消息气泡和当前会话；OCR 只作为可见区域降级手段。
- UIA 无法给出气泡边界时，退回 `visible_snapshot`，不要伪造逐条消息。
- 采集器只观察当前会话，不为了补消息自动操作用户微信。

### 6.3 会话与消息身份

- 使用稳定会话标识作为 `source_id`，窗口标题只作为显示名和降级线索。
- 授权向导列出实际检测到的会话，由用户逐个允许；默认 deny。
- 为每个会话持久化最近一次可见气泡序列和检查点。
- 新快照与旧快照做有序重叠匹配，只发射新增后缀；相同文本连续出现两次仍是两条合法消息。
- 每条新消息分配持久 `event_id`，Spool 重试和服务端幂等均使用该 ID。
- 重启后恢复上次快照，避免把当前可见历史全部重新入库。
- 如果重启或页面变化后无法可靠对齐，标记 `partial/unknown` 并保留缺口，不大批量重复导入，也不假装没有漏消息。

### 6.4 微信字段

消息至少区分：

- 会话标识与显示名。
- 发送者：可识别则记录，否则 `unknown`。
- 方向：自己、对方或 `unknown`。
- 正文、消息类型、观察时间、可选真实时间。
- 完整性、证据引用和授权策略版本。

后续“回复微信”仍属于外部动作，必须走 ActionOutbox 人工审批；消息监听权限不隐含发送权限。

## 7. 网页监听改造

保留 Playwright、Readability、授权 URL 和登录安全边界，补四项：

1. **调度与浏览器解耦**：桌面启动后恢复启用站点的调度；只有真正运行站点时才加载浏览器会话。
2. **持久调度状态**：保存 `last_run_at`、`next_due_at`、最近成功、最近错误和运行租约，重启后按原计划继续，不立即重复全站抓取。
3. **页面检查点**：每个页面在服务端确认后保存规范 URL、内容 hash、最近观察与最近变更；失败页面不推进成功检查点。
4. **变更语义**：无变化不生成新工作；新增和更新形成不同事件，无法比较时标 `unknown`。首版不为了“语义去重”每次调用模型。

同一 URL 继续归并到同一 Thread，内容变化形成新版本；站点导航仍不得跳出授权 origin／路径，不绕过登录、验证码或反自动化机制。

## 8. 工作轨迹与 Episode 改造

### 8.1 保留现有观察链路

继续保留当前窗口／当前标签页正文、UIA＋OCR、变化才去重、本地 JSONL、独立轨迹窗口、阶段总结和截图保留策略。不要把原始轨迹全部上传为 Trigger，也不要默认把所有截图发给模型。

### 8.2 从“按时间总结”升级为“按工作上下文分段”

时间仍作为兜底边界，同时加入确定性分段信号：

- 项目目录、文档或页面主体变化。
- 应用与窗口语义明显变化。
- 长时间空闲或用户明确切换工作。
- 达到最大片段时长或事件预算。

允许同一项目跨多个应用组成一个 Episode，但跨项目不能仅因为发生在同一天就合并。

### 8.3 Thread 与任务关联

- 高置信度上下文使用 `activity:<context_key>` 作为活动 Thread。
- 无法判断上下文时进入 `activity:unassigned:<日期>`，不要强行归入某个项目。
- “按天查看全部活动”改为查询视图，不再要求所有活动共用一个物理 Thread。
- Episode 增加项目／文档候选、涉及应用、起止时间、证据引用、摘要、输出与问题。
- 项目或 WorkTask 匹配置信度不足时只生成关联建议，由用户或 Router 确认，不直接修改 Live State。
- Episode 上报也进入 Spool，失败后可见且可重试。

## 9. 隐私、证据与模型上下文

1. 采集、摘要、索引、简报、自动 Worker 继续独立授权；开启监听不等于允许自动执行任务。
2. 未授权来源不进入 Spool 正文、Trigger、向量、摘要、简报或旧通知中心。
3. 原始截图与长正文默认只留本机，模型优先接收摘要、必要片段和证据引用。
4. 需要补看证据时通过有权限、可审计的读取接口获取，不因持有 `evidence_ref` 就绕过授权。
5. 敏感命中继续执行脱敏并丢弃敏感截图；撤销授权同时清理待发正文。
6. 微信、网页和工具返回文本都是不可信数据，其中的“忽略规则、发送密钥、自动执行”等文字只能作为内容处理。
7. 摘要必须保留完整性语义，不能把“当前可见片段”总结成“全部聊天记录”。

## 11. 分阶段实施顺序

### M0：先让采集可靠且可解释

- 统一 Observation Envelope、持久 Spool、幂等和健康状态。
- 明确 observed／delivered／filtered／failed 四种状态。
- 复验上一轮新架构的 Router、ToolGateway 和 Checkpoint 阻断项。
- 此阶段不扩大自动 Worker 范围。

### M1：电脑微信当前会话 MVP

- 独立连接器、逐会话授权、气泡增量、重复文本处理、重启恢复。
- 提供测试采集和真实错误展示。
- 先验收当前会话，不以快照功能冒充后台全量监听。

### M2：网页监听可靠性

- 启动恢复、持久调度、页面检查点和变更类型。
- 补服务停止、桌面重启和登录失效后的恢复。

### M3：工作 Episode 语义化

- 项目／文档上下文分段、活动 Thread 拆分、证据引用和 Episode 重试。
- 低置信度只给任务关联建议。

### M4：接入新架构并做综合评估

- 在权限门禁复验通过后，再接 Router、WorkTask Inbox、Memory 和 Brief。
- 对跨渠道同一任务做归并测试，对无关事件做隔离测试。
- 用真实微信、真实网页和真实桌面工作验收，不以单元测试替代真机结果。

## 12. 必过验收题

### 微信真机

1. 只允许一个测试会话，另一会话保持未授权。
2. 在允许会话接收两条真实新消息，界面能区分观察与入库时间。
3. 同一发送者连续发送两次完全相同文本，必须保留两条。
4. 切换会话不串线，未授权会话正文不入库、不进入模型。
5. 服务停止后收到新消息，恢复后可重试入库且用户能看到待发状态。
6. 桌面端重启不重复导入可见历史，也不因内存去重丢失合法消息。
7. 上传失败、来源被过滤、UIA 无法识别分别显示不同状态。
8. 无法识别发送者或真实时间时显示 `unknown`，不编造。
9. 无法可靠对齐重启前后的消息时明确存在缺口，不静默重复或假装完整。

### 网页

1. 桌面重启后启用站点按原调度恢复，不立即重复抓取全部页面。
2. 页面无变化不生成重复工作，正文变化形成同 Thread 的新版本。
3. 上传失败的页面不推进成功检查点，恢复后幂等补交。
4. 登录失效、跳转未授权 origin、路径越界均停止并显示原因。
5. 未打开 Workbench 时，启用站点仍能按设计运行后台调度。

### 工作轨迹

1. 同一天处理两个项目时，活动不强制混入一个 Thread。
2. 无正文变化只移动鼠标时不新增内容事件。
3. Episode 上传失败可恢复，重启不重复生成任务。
4. 项目匹配置信度不足时不自动改写 WorkTask。
5. 截图过期后证据状态明确，摘要仍可追溯但不可伪称截图存在。
6. 隐藏主聊天窗口不关闭工作轨迹；关闭微信监听也不应依赖轨迹窗口状态。

## 13. 最终产品口径

M1 真机验收已通过当前会话可见内容与重启幂等检查。界面和文档应称为“已授权当前会话的可见消息增量记录”，不能称为“微信消息监听已完成”，也不能承诺后台全量同步。

当前实现仍受 OCR 限制：图片消息内文字可能误识别或漏行；会话标识第一版以标题为稳定键。只有未来存在合规、稳定、经过真机验证的后台来源，才可以另行承诺更完整的同步能力。
